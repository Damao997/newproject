# 即席分析模块技术方案（方案 B）

> 文档定位：**可评审技术方案**（docs/plans/）。针对「经营分析（`/dashboard/analysis/*`）」与「映射管理（`/data/board/*`）」合并为「即席分析 / 自定义报表」模块的**方案 B —— 后端参数化聚合**。本文只定义接口契约与改造点，不含实现代码。评审通过后再进入开发。
>
> 前置阅读：`docs/plans/整体方案v3.md`（架构）、`docs/plans/安全与权限规范.md`（权限）、`docs/plans/数据模型规范.md`（数据模型）。冲突时以本文件为准（仅限本模块范围）。

## 1. 背景与目标

### 1.1 问题

经营分析与映射管理是同一链路的「配置端」与「消费端」，却被放在两个互不相通的页面：

| 经营分析子页 | 行维度来源 | 映射管理对应面板      |
| ------ | ----- | ------------- |
| 核心指标分析 | 产品    | 产品配置          |
| 品类预算达成 | 品类    | 品类配置          |
| 运营费用分析 | 费用映射  | 运营费用映射        |
| 公司预算达成 | 主体    | 主体配置 + 月度预算比例 |

另外 4 个子页（关键指标概览、现金流量分析、应收账龄分析、存货分析）的行维度来自科目树 / 往来 / 存货，与映射管理无关。

现状痛点：改一次映射要跨模块切换；8 个子页的行列组合全部固定，用户无法按自己的口径组合「行维度 × 指标列」。

### 1.2 目标

1. 后端提供一个**通用分析查询接口**，以「行维度 × 指标列」为参数返回统一结构的二维结果。
2. 前端据此提供**工作台**：分析区自由组合行列，配置区就地维护映射，改动即时反映。
3. 保留「保存为自定义视图」的扩展位（P2 落地）。

### 1.3 非目标

- **不实现**任意维度自由组合的 BI（受 §2 数据模型约束，需先做方案 C 的维度规范化）。
- **不重构**现有聚合算法（`AggregationService` 的科目树构建、重分类回放、汇总展开全部复用）。
- **不改变**现有 8 个子页的口径与展示形态（迁移期新旧接口并存，口径必须逐字段一致）。
- **不新建**事实表、不新增维度列。

## 2. 现状约束（决定了「有限即席」的边界）

| 约束            | 证据                                                                                                                                                          | 对方案的直接影响                                     |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 事实表无业务维度列     | `fact_operating` 唯一键 `[companyCode, accountCode, period, periodDimCode]`（`server/prisma/schema.prisma:367`）                                                 | 行维度只能来自「科目树 + 配置表运行时匹配」，不能是 SQL `GROUP BY` 列 |
| 维度成员靠运行时字符串匹配 | `matchProductCategories`（`server/src/services/DashboardService.ts:586`）按 `subjectKeyword` 对科目名 `includes`；`matchExpenseMappings`（`:536`）按 `subjectCodes` 求和 | 行维度实现为**适配器**而非查询条件；匹配函数已存在且为纯函数，可直接复用       |
| 各子页硬编码        | `getProductBudget:862`、`getExpenseAnalysis:900`、`getKeyMetrics:944`、`getProductMetrics:1120`、`getSubjectBudget:1185`                                        | 差异只在「行怎么取」与「列怎么投影」，聚合底座同源                    |
| 入参签名已统一       | 上述方法签名均为 `(scope, { period, companyCode })`                                                                                                                 | 抽象时机已到，改造成本可控                                |

### 2.1 关键判断：这是一次低风险重构

现有代码中**通用能力已经存在**，只是被包在各子页内部：

- `keyMetricsGroup()`（`DashboardService.ts:184`）是**纯函数**，已产出预算 / 实际 / 同比 / 环比 / 达成率的完整口径结构 —— 即「指标字典」的计算内核。
- `matchProductCategories` / `matchExpenseMappings` 是**已 export 的纯函数** —— 即「行维度适配器」的内核。
- `AggregationService.buildOperatingTree(codes, period, opts)`（`AggregationService.ts:465`）是**科目树聚合的唯一入口**，含重分类回放（`opts.excludeReclassify`）与汇总抵消（`opts.consolidationSummaryCode`）。

**因此本方案不需要重写聚合逻辑，只需新增一层「选择器」**：把「行维度选择」与「指标列投影」参数化。

## 3. 总体设计

```
                 ┌─────────────────────────────────────────┐
  请求 spec ───▶ │  AnalysisQueryService（新增·编排层）      │
                 │  1. 解析并校验 spec（zod）                │
                 │  2. 解析生效主体/期间（复用现有解析器）      │
                 │  3. 构建科目树（AggregationService）       │
                 │  4. 按 rowDim 选适配器 → 生成行             │
                 │  5. 按 metrics 投影列 → 生成 values         │
                 └─────────────────────────────────────────┘
                        │                │              │
            ┌───────────┘                │              └───────────┐
            ▼                            ▼                          ▼
   RowAdapter 注册表            MetricCatalog 指标字典      AggregationService（复用）
   product / category /         key → { header, tip,        buildOperatingTree
   expense / subject /          valueType, group, pick }    （含重分类/汇总）
   company
```

**核心抽象两条**：

1. RowAdapter（行维度适配器） —— 输入「科目树 + 配置 + 上下文」，输出统一行数组。
2. **MetricCatalog（指标字典）** —— 输入 `KeyMetricsGroup`，输出可投影的指标集合。

两者均为纯函数注册表，可独立单测。

## 4. 接口契约

### 4.1 端点

```
POST /api/v1/dashboard/analysis/query
```

- **方法选择**：查询描述含数组字段（`metrics` / `rowCodes`），GET 查询串冗长且需转义；POST 语义为「提交查询描述」，非创建资源。
- **权限**：`requirePermission('dashboard:view', 'view')`，与现有经营分析端点一致 —— **不新增权限码，零权限迁移成本**。
- **中间件链**：沿用 `routes/dashboard.ts` 现有链（`authenticate` → `attachScope()` → 路由级 `requirePermission`）。
- **响应封装**：`sendOk(res, data)`（`server/src/lib/response.ts`），自动带 `traceId`。

> 待评审决策 D1：端点归属。选项 A 挂 `/dashboard/analysis/query`（与现有经营分析同域，权限复用最自然）；选项 B 新建 `/analysis/query`（语义更独立，但需新增路由文件与权限码）。

### 4.2 请求体

```jsonc
{
  // ── 口径 ──
  "companyCode": "EN330059",   // 可选 string。缺省按用户 scope 汇总；汇总主体编码自动展开成员
  "period": "2026-09",         // 可选 string（YYYY-MM）。缺省取最新可用期间

  // ── 行 ──
  "rowDim": "product",         // 必填。product | category | expense | subject | company
  "filters": {
    "excludeReclassify": false, // 可选 bool。去重分类模拟口径（复用 AggregationService 回放）
    "keyword": "",              // 可选 string。行名关键字过滤
    "rowCodes": []               // 可选 string[]。限定行成员编码（空=全部）
  },

  // ── 列 ──
  "metrics": [                 // 可选 string[]。缺省取该 rowDim 的默认列集
    "income.ytdBudget", "income.ytdActual", "income.alertRate", "income.ytdYoy"
  ],

  // ── 输出控制 ──
  "options": {
    "includeEmptyRows": false, // 可选 bool。true 时保留零值行（品类全量展示场景）
    "includeTotals": true,     // 可选 bool。是否返回合计行
    "level": null              // 可选 number|null。仅 rowDim=subject 时生效，按科目层级过滤
  }
}
```

**校验规则（zod）**：

| 字段                   | 规则                                                            |
| -------------------- | ------------------------------------------------------------- |
| `rowDim`             | 枚举必填                                                          |
| `period`             | `/^\d{4}-\d{2}$/`，且必须 ∈ `availablePeriods()`，否则 400           |
| `metrics[]`          | 元素必须 ∈ MetricCatalog 的 key 集合（多组维度须带组前缀），长度 ≤ 60；非法 key → 400（**不静默忽略**）。**实现修正**：原设 ≤30，但多组维度「全选」需 2 组 × 19 = 38（product）/ 3 组 × 19 = 57（company），30 会让这两类维度无法全选，故放宽至 60 |
| `filters.rowCodes[]` | 长度 ≤ 500                                                      |
| `options.level`      | 0 ≤ n ≤ 3，仅 subject 维度有效                                      |

### 4.3 响应体

```jsonc
{
  "code": 0,
  "message": "success",
  "traceId": "uuid-v4",
  "data": {
    // ── 生效口径回显（前端展示用，避免前后端口径不一致的静默偏差）──
    "period": "2026-09",
    "rowDim": "product",
    "companyCode": "EN330059",
    "companyName": "杭州分公司",
    "companyType": "single",        // single | summary | null
    "degraded": false,              // 权限回退标记（与现有接口同义）

    // ── 列定义（后端下发，前端按 valueType 渲染）──

      {
        "key": "ytdActual",
        "header": "财年累计达成",
        "valueType": "amount",      // amount | ratio | quantity
        "group": "收入",             // 表头分组（可选）
        "tip": "年初至当期的累计实际值"

        }
      }

    // ── 合计行（includeTotals=true 时）──
    "totals": {
      "values": { "income.ytdActual": 9800.00, "income.ytdBudget": 12000.00, "income.alertRate": 81.67, "income.ytdYoy": 4.10 }
```

### 4.4 契约设计说明

| 决策                                                | 理由                                                                                                           |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `values` 用 `Record<metricKey, number\|null>` 统一承载 | 这是与现状的本质区别：现有各子页返回结构互不相同（`ProductMetricsRow` 有 `income`/`profit` 两组、`SubjectBudgetRow` 另一套），前端无法泛化渲染         |
| `columns` 由后端下发                                   | 列的口径（header / 单位 / 提示 / 分组）属于业务定义，后端下发后新增指标不必改前端                                                             |
| `null` 语义 = 「不适用」                                 | 与现有前端约定一致（无预算显示「—」，见 `core-metrics-content.tsx:32`）                                                          |
| 回显生效口径                                            | 现有 `ProductMetricsResult` 已含 `companyCode/companyName/companyType/degraded`（`DashboardService.ts:172`），沿用该模式 |
| 金额单位万元、比率两位小数                                     | 全站统一口径（`CLAUDE.md` 金额展示节）                                                                                    |
| **多指标组维度的 key 前缀**（D3 落地）                        | 单组维度（expense / subject）用裸 key（`ytdActual`）；多组维度（product / category 2 组、company 3 组）用 `组名.key`（`income.ytdActual`）。跨组派生指标（`marginRate`）恒用裸 key —— 它同时读收入与毛利，不隶属任何单组 |

> 待评审决策 D2：`columns` 由后端下发还是前端维护。选项 A 后端下发（本方案默认，扩展性好）；选项 B 前端维护（改动更小，但新增指标需前后端同步发版）。

## 5. 指标字典（MetricCatalog）

`KeyMetricsGroup`（`DashboardService.ts:120`）已涵盖预算 / 实际 / 同比 / 环比 / 达成率全部口径，MetricCatalog 在其上做**投影 + 派生**。

### 5.1 直通指标（`pick` = 取 `KeyMetricsGroup` 同名字段）

| metricKey        | header  | valueType |
| ---------------- | ------- | --------- |
| `monthActual`    | 本月达成    | amount    |
| `monthBudget`    | 本月预算    | amount    |
| `monthSame`      | 去年同期    | amount    |
| `monthChange`    | 同比变动额   | amount    |
| `monthYoy`       | 同比      | ratio     |
| `monthMomChange` | 环比变动额   | amount    |
| `monthMom`       | 环比      | ratio     |
| `monthRate`      | 本月完成率   | ratio     |
| `annualBudget`   | 财年预算目标  | amount    |
| `ytdBudget`      | 累计预算目标  | amount    |
| `ytdActual`      | 财年累计达成  | amount    |
| `ytdSame`        | 同期累计    | amount    |
| `ytdChange`      | 累计同比变动额 | amount    |
| `ytdYoy`         | 财年同比    | ratio     |
| `annualRate`     | 年度完成率   | ratio     |

### 5.2 派生指标（当前由前端计算，本方案下沉到后端）

| metricKey    | header | 口径                                                        | 现状位置                          |
| ------------ | ------ | --------------------------------------------------------- | ----------------------------- |
| `deviation`  | 累计偏差额  | `ytdActual − ytdBudget`（`ytdBudget` 为空则 null）             | `core-metrics-content.tsx:49` |
| `alertRate`  | 预警达成率  | `ytdActual ÷ ytdBudget × 100`（三档：<60 红 / 60–75 黄 / ≥75 绿） | `core-metrics-content.tsx:56` |
| `share`      | 贡献占比   | `行值 ÷ totals 值 × 100`（需 totals，**故必须后端算**）                | `core-metrics-content.tsx:62` |
| `marginRate` | 毛利率    | `毛利 ÷ 收入 × 100`（仅 rowDim=product 且取 profit/income 双组时可用）  | `core-metrics-content.tsx:68` |

> **为什么 `share` 必须下沉**：即席分析下前端不知道全貌（行集合由后端决定），占比的分母只能后端提供。

> **`marginRate` 是跨组指标**：它同时读收入与毛利两组，故**恒用裸 key**（不带组前缀），且仅在同时具备 `income` + `profit` 两组的维度（product / category / company）可用；用于单组维度（expense / subject）返回 400。

> **口径对照（实现核对）**：`ProductBudgetMetric.ytdRate`（累计实际 ÷ 年度预算总额）对应本字典的 **`annualRate`**；预警用的 `ProductBudgetMetric.ytdCumRate`（累计实际 ÷ 累计预算）对应 **`alertRate`**。原方案示例中的 `ytdRate` 并非字典内的独立指标，已修正为 `alertRate`。

> 待评审决策 D3：`marginRate` 需要「收入 + 毛利」双组口径，而本接口的 `values` 是单组结构。选项 A 在 product 维度下将 income/profit 双组扁平化为 `income.ytdActual` / `profit.ytdActual` 形式的 key（本方案倾向，兼容现有展示）；选项 B 扩展 `values` 为嵌套双组（结构更清晰，但偏离统一契约）。

## 6. 行维度适配器（RowAdapter）

统一签名：

```ts
type RowAdapter = (ctx: {
  tree: ValueNode[]                 // AggregationService.buildOperatingTree 结果
  ratios: number[] | null           // BudgetRatioService.budgetRatiosOf(fiscalYear)
  monthIndex: number                // 当期在财年中的月份索引
  filters: QueryFilters
  options: QueryOptions
}) => Promise<{ rows: QueryRow[]; totals?: QueryRow; unmatched: string[] }>
```

| rowDim     | 实现来源                                                                                                                   | 复用情况                                      |
| ---------- | ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| `product`  | `matchProductCategories(products, incomeRoots, profitByName, ratios, monthIndex, keepEmpty)`，配置源 `key_metrics_product` | **直接复用**（`DashboardService.ts:1166` 同款调用） |
| `category` | 同上，配置源 `product_category`                                                                                              | **直接复用**（`getProductBudget` 同款）           |
| `expense`  | `matchExpenseMappings(mappings, tree, ratios, monthIndex)`，配置源 `expense_subject_mapping`                               | **直接复用**（`getExpenseAnalysis` 同款）         |
| `subject`  | 遍历 `flattenValueTree(tree)`，按 `options.level` 与 `filters.keyword` 过滤                                                   | 新增（逻辑简单，仅遍历投影）                            |
| `company`  | 对每个主体分别调用 `buildOperatingTree` 后取值                                                                                     | **新增，注意性能**（见 §10 风险 R2）                  |

**合计行（totals）**：

- `product` / `category`：合计取**整体顶层节点**（「壹品慧收入」/「壹品慧毛利」），**非行求和** —— 因关键词可重叠、层级可嵌套，行求和会重复统计（现有实现即如此，`core-metrics-content.tsx:164` 注释明确「产品含层级，不能直接相加」）。与 `getProductMetrics.totals` 逐字段一致。
- `expense`：合计 = 全部映射科目的**并集**求和（同一科目被多条映射覆盖时不重复相加），与 `getKeyMetrics` 的「运营费用」合计行同口径。
- `subject`：**不产出合计行** —— 各顶层类别（收入 / 费用 / 现金 / 指标…）语义不同，相加无业务含义。请求 `includeTotals=true` 时该维度仍不返回 `totals`。
- `company`：合计为**全部授权主体**（`ctx.companyCodes`）的汇总聚合。
- `options.includeTotals=false` 时响应不含 `totals` 字段（但 `share` 的分母仍内部计算，不受该开关影响）。

## 14. 子项 C1：映射显式化（混合模式）

> 定位：本方案 P1.5 的独立子项。**不改变** §4 接口契约，只增强 §6 行维度适配器中 `product` / `category` 两个维度的**配置来源**。

### 14.1 问题与目标

§6 中 `product` / `category` 两个维度的配置源（`key_metrics_product` / `product_category`）当前**只有 `subjectKeyword` 一个字段**，运行时按科目名 `includes` 匹配（`matchProductCategories`）。这种「隐式匹配」有三类固有缺陷：

| 缺陷 | 场景 | 后果 |
| --- | --- | --- |
| **科目改名即失效** | 关键词「灶具」原命中「灶具收入」；科目改名为「厨房电器收入」后不再命中 | 该行**静默消失**，无任何报错 |
| **关键词重叠** | 关键词「服务」同时命中「服务类收入」与「增值服务收入」 | 行内容与预期不符，且难以定位 |
| **无法精确表达** | 某品类需由 3 个**不相邻**且名称无共同子串的科目组成 | 只能靠多关键词并集近似，无法保证精确 |

C1 引入 **`subjectCodes`（显式科目编码数组）**，形成**混合模式**：

- `subjectCodes` **非空** → 按科目编码**精确匹配**（显式，稳定，不受改名/重构影响）；
- `subjectCodes` **为空** → 回退 `subjectKeyword` 关键词匹配（自动，保持改造前行为）。

> **业务前提（已确认）**：接受「**显式覆盖需人工维护**」—— 显式配置后科目调整不再自动跟随，由业务在 `check` 提示下人工维护。

### 14.2 数据模型

`ProductCategory` 与 `KeyMetricsProduct` 各新增一列：

```prisma
subjectCodes String[] @default([]) @map("subject_codes")
```

迁移 `20261016022217_add_subject_codes_to_mapping_configs`：

```sql
ALTER TABLE "key_metrics_product" ADD COLUMN "subject_codes" TEXT[] DEFAULT ARRAY[]::TEXT[];
ALTER TABLE "product_category"     ADD COLUMN "subject_codes" TEXT[] DEFAULT ARRAY[]::TEXT[];
ALTER TABLE "user_preference"      ALTER COLUMN "updated_at" DROP DEFAULT;
```

> 第三行是**历史 schema drift 修正**（`schema.prisma` 中 `updatedAt` 无 `@default`），与 C1 无关，随本次迁移一并收敛。
> **默认空数组 = 全量回退关键词**，故迁移对存量数据**零行为影响**。

### 14.3 匹配语义（收敛规则）

新增纯函数 `resolveCategoryMembers(cat, allNodes, incomeRoots)`（`DashboardService.ts:589`），两种模式**共用**「祖先已命中则后代剔除」的收敛规则：

- **原因**：祖先节点值 = 全部后代之和，父子同时命中会**重复求和**（如关键词命中「直饮水业务回款」及其子科目）。
- **去重键**：显式模式 = `n.code`；关键词模式 = `n.name`（与改造前语义一致）。

| 模式 | 命中判定 | 去重键 |
| --- | --- | --- |
| 显式 | `codes.has(n.code)` | `n.code` |
| 关键词 | 任一关键词 `n.name.includes(kw)` | `n.name` |

`matchProductCategories` 循环内由内联关键词逻辑改为调用该函数，**其后 income / profit / covered / uncovered 逻辑完全不变**。

### 14.4 服务层改造

`ProductCategoryService` / `ProductConfigService`（**对称改造**）：

| 改造点 | 内容 |
| --- | --- |
| DTO | 新增 `subjectCodes: string[]`；`toDto` 兜底 `?? []` |
| `normalizeCodes()` | 新增：去空白、去空串、去重（保留首次出现顺序） |
| `nodeOf(code, name, category, level)` | **补上 `code`**（见 §14.5） |
| `create` / `update` | 校验放宽为「**关键词与显式科目至少一个非空**」（允许纯显式配置） |
| `check()` | 新增 `brokenCodes`；`brokenKeywords` 在显式模式下返回空 |

`check()` 返回结构（`ProductCategoryCheckResult` / `KeyMetricsProductCheckResult`）：

```
categories          各品类 + matchedSubjects + profitOk
uncoveredSubjects   收入类别中未被任何品类覆盖的节点（新增业务线提示）
brokenKeywords      关键词模式下无命中的关键词（显式模式下恒为空）
brokenCodes         显式模式下在收入科目树中不存在的编码（关键词模式下恒为空）
missingProfitMirror 有命中但毛利镜像缺失的品类
```

### 14.5 实现中修正的两处预估（原方案未预见）

两处均为「**不改会出隐蔽故障**」的点，实现时才发现：

**① `nodeOf` 的科目 code 必须补齐。**

两个 Service 的 `check()` 构建科目树时，节点 `code` 原为 `''`（此前仅供关键词**按名匹配**，code 无意义）。显式模式按 `code` 匹配，若不补齐，则 **`check` 场景下显式配置全部失效** —— 而**主查询链路正常**（`matchProductCategories` 走 `AggregationService.buildOperatingTree` 构建的树，节点自带 code）。

> 这是**最难排查的一类隐蔽故障**：功能本身工作正常，反而是「检测功能」报错，容易被误判为检测逻辑自身的 bug。

**② 校验必须放宽。**

原 `subjectKeyword` 为必填。混合模式需支持「纯显式配置」（不填关键词），故改为「**关键词与显式科目至少一个非空**」：

- `create`：`(!subjectKeyword && subjectCodes.length === 0)` → 400；
- `update`：**双向**校验，防止把回退链清空导致该行**永不命中**（`!nextKeyword && nextCodes.length === 0` → 400）。

### 17.2 关键实现约束：适配器是「直接字段映射」而非「按节点重算」

这是契约测试能够成立的前提。原因：`ytdBudget` 在两条路径上的**边界语义不同** ——

- `ProductBudgetMetric.ytdBudget` = `ytdBudget || null`（**0 → null**）
- `keyMetricsGroup.ytdBudget` = `annualBudget === 0 ? null : round2(v.ytdBudget ?? 0)`（**0 保持 0**）

若适配器改用 `keyMetricsGroup` 重算，会在「年度预算为 0」「占比拆分后累计为 0」两类边界上产生 `null` vs `0` 的**静默差异**。

故 `groupOfProductMetric` / `groupOfExpenseRow` 采用**逐字段直取**（仅 `monthChange` / `ytdChange` / `monthMomChange` 为新增派生），使契约对照断言在正确实现下**恒等** —— 其价值在于捕获适配器**选错数据源、行序错乱、过滤条件不一致**等回归。

### 17.3 契约测试夹具（重要）

**测试库（`yipinhui_finance_test`）没有任何 active 导入批次**（`import_batch` 为空、`fact_operating` 仅 1 行孤儿数据），故契约测试**不能依赖种子数据**，必须自建夹具：

- 唯一公司（`ENAQ<suffix>`）+ 两个 active 批次（经营 / 预算）
- 全量经营叶子科目 × 4 期事实（`2099-05` / `2099-06` / `2098-05` / `2098-06`），覆盖**本月 / 同期 / 本年累计 / 同期累计**四条取数路径
- 全量叶子科目 × 年度预算（`FY2099`，120）
- 一条 `subject_budget_config`（供 company 维度）
- 每期用**不同倍率**（0.7 / 0.9 / 1.0 / 1.1），保证各口径**互不相等** —— 否则「断言相等」无意义
- `afterAll` 硬删除全部夹具；无 DB 时整组跳过

### 18.3 实现要点

1. **列定义的前后端分工（D2 落地）**：后端 `columns` 是口径与渲染的唯一权威；前端 `analysis-metrics.ts` 只负责「列选择器的标签与分组」。新增指标只需后端加定义，前端补一行标签，**不影响已保存的查询**。

4. **配置区零新 CRUD 代码**：直接复用 `components/dimension/*` 的五个映射面板，与「数据管理 · 映射管理」同一批组件；权限显隐与后端 `requirePermission` 一致（CRUD 走 `data:subject:*`，查看需 `data:browse:view`）。
5. **切换不整页 loading**：queryKey 内嵌 spec + `keepPreviousData`，切换维度/指标/主体时保留上一次结果。
