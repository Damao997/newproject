## 一、设计原则

### 1.1 三大范式应用

数据库设计严格遵循三大范式，所有反范式例外均需满足"明确的业务场景 + 严格评估"两个条件。

#### 1NF — 字段原子化

每个字段存储单一、不可分割的值。禁止将多个信息合并到一个字段中。

| 规则 | 违反示例 | 正确做法 |
|------|---------|---------|
| 公司主体编码与名称分离 | `company_info = "EN330059-浙江壹品慧杭州分公司"` | `code = "EN330059"`, `name = "浙江壹品慧杭州分公司"` 分两字段 |
| 期间维度不合并 | `period_info = "2025-06本月实际"` | `period = "2025-06"`, `period_dim_code = "ACTUAL_MONTH"` 分两字段 |
| 汇总映射逗号分隔多值拆为多行 | `single_codes = "EN330059,EN330060,EN330061"` | 在 `company_aggregation_map` 中拆为 3 行，一行一映射关系 |
| 科目列名不编码多义 | 列名 `本月收入` 同时隐含科目和期间维度 | column_map 拆解：`source_column="本月收入" → account_code="OP_02", period_dim="ACTUAL_MONTH"` |

#### 2NF — 消除部分依赖

所有非主键字段必须完全依赖**整个主键**（尤其针对联合主键）。若某字段仅依赖部分主键，应拆分到独立表。

| 规则 | 违反示例 | 正确做法 |
|------|---------|---------|
| 事实表 value 依赖完整复合键 | 若主键含 `company_code` 但 `value` 只依赖 `account_code`，则违反 2NF | `fact_operating` 的 `value` 完全依赖 `(company_code, account_code, period, period_dim_code, batch_id)` 整个复合键 |
| 账龄区间用长表而非宽表 | `aging_record` 宽表设计：`amount_0_1M`, `amount_1_3M`, `amount_3_6M`... 各列仅部分依赖主键 | 长表设计：`(company_code, counterparty_code, account_code, period, bucket_code)` → `amount`，一行一区间 |

#### 3NF — 消除传递依赖

非主键字段之间不能存在传递依赖（即非主键字段不能依赖其他非主键字段）。应拆分为独立表并通过外键关联。

| 规则 | 违反示例 | 正确做法 |
|------|---------|---------|
| 公司名称只存 `company` 表 | 事实表存 `company_name` 字段 → `company_name` 依赖 `company_code`，`company_code` 又依赖主键 | 事实表只存 `company_code` (FK)，名称通过 JOIN `company` 获取 |
| 科目名称只存 `account_subject` 表 | 事实表存 `account_name` 字段 | 事实表只存 `account_code` (FK)，名称通过 JOIN 获取 |
| 期间维度名称只存 `period_dimension` 表 | 事实表存 `period_dim_name` 字段 | 事实表只存 `period_dim_code` (FK) |

**3NF 核心目标**：
- 减少数据冗余 — 同一信息不重复存储
- 保证数据一致性 — 修改一处即可全局生效
- 提升可维护性 — 结构清晰，便于扩展

### 1.2 长表设计策略

**核心问题**：Excel 数据文件是"一行多公司多期间"的**宽表**，数据库 FactRecord 采用**长表**（一行一指标一值）。

**转换策略**：导入时在后端 `ImportService` 执行 **unpivot/melt**（宽表→长表转换），非前端执行。

```
宽表行（Excel）：
{公司:杭州壹品慧, 月份:2025-06, 本月收入:120000, 总成本:80000, ...}

        ↓ ImportService.unpivot()

长表行（数据库）：
{company_code:"EN330059", period:"2025-06", account_code:"OP_0201", period_dim_code:"ACTUAL_MONTH", value:120000}
{company_code:"EN330059", period:"2025-06", account_code:"OP_0301", period_dim_code:"ACTUAL_MONTH", value:80000}
...
```

### 1.3 三张事实表分离理由

经营数据、静态数据、年度预算来自 3 个不同的 Excel 文件，期间维度体系不同：

| 事实表 | 期间维度体系 | 数据来源 |
|--------|-------------|---------|
| `fact_operating` | 经营 5 个：预算金额、本月实际、同期实际、本年累计、同期累计 | 经营数据数据范例.xlsx |
| `fact_static` | 静态 4 个：本期金额、年初金额、同期金额、上年年初金额 | 静态数据范例.xlsx |
| `fact_budget` | 财年 + 月度/年度 | 年度预算范例.xlsx |

分表存储更清晰，符合 3NF（消除不同期间维度体系的传递依赖）。

### 1.4 软删除查询过滤

所有标记 `status` 字段的表（`company`、`account_subject`、`counterparty`、`user`、`role`、`metric` 等），**业务查询必须过滤 `status = 'active'`**。

- 通过 Prisma 扩展层（`softDelete.ts`）统一注入过滤条件，避免遗漏
- 软删除数据泄漏到查询结果视为 Bug

### 1.5 反范式例外规则

为查询性能可适当冗余，但需满足**两个条件**：
1. 有明确的业务场景驱动
2. 已严格评估必要性及数据不一致风险

**允许的反范式示例**：

| 表 | 字段 | 理由 |
|----|------|------|
| `transaction_detail` | `closing_balance` | 期末余额 = 期初 + 借方 - 贷方，虽可计算，但作为高频查询字段保留。一致性风险可控：单一导入批次内计算确定 |
| `transaction_detail` | `aging_1m` ~ `aging_3y_plus` + `aging_total`（11 列宽表账龄） | ERP 导出报表原生为 10 段宽表账龄，导入保持原始行结构，避免行级明细拆 10 倍行数；跨客商的长表聚合分析由 `aging_record`（长表设计，见 6.2 节）承担 |
| `transaction_detail` | `company_name`、`counterparty_name` | 导入时的名称快照。往来数据源自外部 ERP，客商/公司名称可能与主数据不同步，保留原文用于追溯与对账展示 |

### 1.6 容量规划

| 指标 | 数值 |
|------|------|
| 经营数据年增量 | ~22 万行/年（10公司 × 12月 × 5期间维度 × ~70科目 × ~5.3） |
| 静态数据年增量 | ~1,360 行/批次（10公司 × 34科目 × 4期间维度） |
| 3 年数据总量 | ~66 万行 |
| 存储空间 | ~108 MB/年（含索引） |
| 单次导入 unpivot 经营数据 | ~18,240 行/批次（10公司 × 12月 × ~152科目） |
| 单次导入 unpivot 静态数据 | ~1,360 行/批次 |

## 二、命名规范

> 本章为数据库对象命名的唯一标准。**现状即标准**：当前 `schema.prisma` 全部 37 张在用表已满足本章规则，不产生存量整改项；本章用于约束后续新增/变更。

### 2.1 表命名

| 规则 | 说明 | 示例 |
|------|------|------|
| snake_case | 全小写 + 下划线，禁止大写、连字符 | `account_subject` |
| **单数形式** | 表名一律单数，禁止复数 | `user`（非 `users`）、`metric`（非 `metrics`） |
| 无库级统一前缀 | 不使用 `t_`/`tbl_` 等统一前缀 | `company`（非 `t_company`） |
| Prisma 模型 PascalCase + 强制 `@@map` | 每个 model 必须显式声明 `@@map("snake_case表名")`，即使模型名小写后与表名一致 | `model AccountSubject { @@map("account_subject") }` |

### 2.2 列命名

| 规则 | 说明 | 示例 |
|------|------|------|
| 数据库列 snake_case | 所有物理列名全小写 + 下划线 | `company_code` |
| Prisma 字段 camelCase | 应用层字段一律 camelCase | `companyCode` |
| 多词字段强制 `@map` | 含大写字母的 Prisma 字段必须 `@map("snake_case")`，且值为字段名的标准 snake_case 转换 | `companyCode String @map("company_code")` |
| 单词字段可省略 `@map` | 单词字段 camelCase 与 snake_case 天然一致 | `code`、`name`、`status` |

### 2.3 前缀约定（域前缀）

| 前缀 | 适用范围 | 现有表 |
|------|---------|--------|
| `fact_` | **仅限**三张 Excel 导入事实表（长表设计、批次生命周期管理） | `fact_operating`、`fact_static`、`fact_budget` |
| `ai_` | AI 域配置表 | `ai_desensitize_config` |
| （无前缀） | 维度表 / 业务表 / 系统表。**边界说明**：往来明细、账龄、存货虽具事实性质，但属"业务表"分区，**不加** `fact_` 前缀 | `transaction_detail`、`aging_record`、`inventory_record` |

### 2.4 后缀语义字典

新表命名必须按下表选择后缀，同一语义禁止再引入新后缀：

| 后缀 | 语义 | 现有表 |
|------|------|--------|
| `_log` | **append-only 事件/流水记录**（只增不改；`reclassification_log` 例外允许回填 `reverted_at/reverted_by` 撤销标记） | `audit_log`、`collection_log`、`enterprise_query_log`、`reclassification_log` |
| `_version` | **内容快照版本**：每版保存完整 snapshot，可回看/回滚 | `report_version` |
| `_history` | **口径/定义变更留痕**：记录"定义"随版本的演进（含变更人/审批人），非内容快照 | `metric_definition_history` |
| `_map` | **纯 N:N 关联表**（仅存两侧外键 + 关系属性） | `company_aggregation_map` |
| `_scheme` | **配置方案表**（非关联表）。注意与 `_map` 区分：`mapping_scheme` 是导入列映射"方案"实体，非 N:N 关联 | `mapping_scheme` |
| `_record` | **周期性业务记录**（一行一期间/一区间） | `aging_record`、`inventory_record` |
| `_detail` | **行级明细**（一行一原始业务单据行） | `transaction_detail` |

### 2.5 保留字规则

- **新表禁用 PostgreSQL 保留字**：`user`、`order`、`group`、`table`、`check`、`default`、`grant` 等（完整清单见 PostgreSQL 官方文档 SQL Key Words）。
- **存量例外**：`user` 表保留不重命名。代价：原生 SQL 中必须写双引号 `"user"`（先例见 `prisma/init-audit.sql` 中 `REFERENCES "user"(id)`）；Prisma Client 查询不受影响（自动加引号）。

### 2.6 枚举值命名

- 枚举类型名 PascalCase（如 `RecordStatus`），枚举值统一**小写 snake_case**（如 `active`、`fiscal_year`、`bad_debt`）。
- **存量例外**：`AgingBucket` 落库值为 `0_1M`/`1_3M`/`3_6M`/`6_12M`/`1_2Y`/`2Y_PLUS`（含大写，因数字开头需 Prisma 值级 `@map`）。不整改（涉及存量数据），**新枚举不得效仿**。

### 2.7 迁移纪律

- 任何表/列重命名必须通过 Prisma migration（`ALTER TABLE ... RENAME`）落地，并**同步更新** `@@map`/`@map`，禁止手工改库。
- 命名合规由 `server/scripts/check-schema-naming.mjs` 守护（pre-commit 触发，见根目录 `lint-staged.config.mjs`）。

## 三、编码规则

### 3.1 公司编码

| 类型 | 格式 | 示例 | 说明 |
|------|------|------|------|
| **单体公司** | `EN` + 6位数字 | `EN330059`（浙江壹品慧杭州分公司） | 前缀 `EN`(Entity) 使程序可直接区分单体/汇总，无需查表 |
| **汇总主体** | `ET` + 4位数字 | `ET0001`（浙江省公司汇总） | 前缀 `ET`(Entity Total) 使程序可直接区分单体/汇总，无需查表 |

> **v1.2 更正**：v1.0/v1.1 曾写作 `CO`+6 / `SUM`+4，与实际实现（`prisma/seed-companies.ts` 与 `CLAUDE.md`）及已落库数据不符，现以实现为准更正为 `EN`/`ET`。


数据来源：`分析主体及汇总映射.xlsx`（10 单体 + 10 汇总）。

### 3.2 科目编码

科目编码采用**前缀 + 级联数字**的会计标准层级编码（v1.4 由 `OP_001`~`OP_152` / `ST_001`~`ST_034` 前序平铺编号重构）：

| 规则 | 说明 | 示例 |
|------|------|------|
| 格式 | `OP_` / `ST_` 前缀 + 级联数字，**每级 2 位**，子码 = 父码数字段 + 本级序号 | 收入=`OP_02`，壹品慧收入=`OP_0201`，增值业务收入=`OP_020101`，燃气具-灶具收入=`OP_0201010101` |
| 长度 | 2 × (level + 1) 位，最长 10 位（经营 5 级 level 0-4） | `OP_0201010101`（10 位） |
| level0 段位 | 段位表登记（见下），新增 level0 大类必须登记，未登记抛错 | 回款=`01`、资产类=`10`+ |
| 层级语义 | 编码自带层级（前 N 位 = 父码），排序即树序，可通过前缀长度识别层级 | `OP_0201` 是 `OP_02` 的子级 |

**经营科目 level0 段位表**（01-08）：

| 段位 | 大类（category） | 段位 | 大类（category） |
|------|-----------------|------|-----------------|
| 01 | 回款 | 05 | 费用 |
| 02 | 收入 | 06 | 经营指标 |
| 03 | 成本 | 07 | 财务指标 |
| 04 | 毛利 | 08 | 现金流指标 |

**静态科目 level0 段位表**（按会计大类分段：资产 10-19 / 负债 20-29 / 权益 30-39 / 比率 40-49）：

| 段位 | 科目（category） | 段位 | 科目（category） |
|------|-----------------|------|-----------------|
| 10 | 总资产 | 21 | 预收账款 |
| 11 | 银行存款 | 22 | 应付账款 |
| 12 | 应收账款 | 23 | 内部往来 |
| 13 | 存货 | 24 | 应付股利 |
| 14 | 固定资产净值 | 30 | 权益净资产 |
| 15 | 在建工程 | 31 | 累计未分配利润(万元) |
| 20 | 总负债 | 40-44 | 总资产报酬率（ROA,%）/ 资产负债率(%) / 净资产回报率（ROE,%）/ 存货周转天数 / 应收账款周转天数 |

**编码示例**：
- 收入=`OP_02` → 壹品慧收入=`OP_0201` → 增值业务收入=`OP_020101` → 厨房产品销售收入（不含净水及服务）=`OP_02010101` → 燃气具-灶具收入=`OP_0201010101`
- 应收账款=`ST_12` → 集团内客户（含城燃体系）=`ST_1201`；存货=`ST_13` → 壁挂炉=`ST_1301`

**生成与维护**：
- 种子/前端 mock 均由 `decorateTree`（`server/prisma/seed-data/subject-trees.ts` 与 `web/src/lib/subject-tree.ts`）按段位表级联生成，两处 `SUBJECT_SEGMENT_MAP` 必须保持一致
- 存量数据迁移：`server/scripts/migrate-subject-codes.ts`（旧码→新码确定性映射，更新科目/指标/公式/事实/重分类等全部引用，幂等可重跑）

**科目分类（category）**：
- 经营科目大类：回款 / 收入 / 成本 / 毛利 / 费用 / 经营指标 / 财务指标 / 现金流指标
- 静态科目大类：资产 / 负债 / 权益 / 比率指标

### 3.3 指标编码

| 指标类型（data_type） | 编码规则 | 示例 |
|----------------------|----------|------|
| **data（数据类）** | `metric.code = account_subject.code` | `OP_0201010101`（燃气具-灶具收入） |
| **display（展示类）** | `metric.code = account_subject.code` | 与科目编码一致（分类汇总节点） |
| **calc（计算类）** | `CALC_` + 业务名称 | `CALC_资产负债率`、`CALC_增值业务毛利率` |

**calc 类型特殊字段**：
- `source_account_codes`（JSON 数组）：记录公式引用了哪些 `account_subject.code`，建立可追溯链路
- `depends_on`（JSON 数组）：记录直接依赖的指标 code，用于 DAG 拓扑排序 + 环检测

> calc 指标 code 使用 `CALC_` 前缀命名空间，与 data/display 类型的科目编码严格区分，避免编码冲突。

**action 字段枚举值**：`view` / `create` / `update` / `delete` / `export` / `import`

## 四、维度表（主数据）

所有维度表数据源自 `分析主体及汇总映射.xlsx`。

### 4.1 公司主体表 `company`

**数据来源**：`分析主体及汇总映射.xlsx` Sheet1（10 单体）+ Sheet2（10 汇总）

| # | 字段 | 类型 | 约束 | 说明 |
|---|------|------|------|------|
| 1 | `id` | UUID | PK | 主键（Prisma: `@id @default(uuid())`） |
| 2 | `code` | VARCHAR | UQ, NOT NULL | 公司编码。单体：`EN`+6位数字（如 `EN330059`）；汇总：`ET`+4位数字（如 `ET0001`） |
| 3 | `name` | VARCHAR | NOT NULL | 公司全称 |
| 4 | `short_name` | VARCHAR(100) | NULLABLE | 公司简称（列表/图表紧凑展示用） |
| 5 | `entity_type` | ENUM | NOT NULL | `single`（单体公司）/ `summary`（汇总主体） |

### 5.5 宽表→长表转换策略（ImportService 7 步流程）

转换流程在后端 `ImportService` 中执行（非前端）。

**Step 1 — 接收原始文件**：multer 接收 FormData 上传的原始 .xlsx 文件，校验 MIME magic number + fileSize ≤ 50MB。

**Step 2 — 识别映射方案**：根据 `data_type` 查询 `mapping_scheme` 表，获取 `column_map` JSON 配置。

**Step 3 — 流式解析**：SheetJS/ExcelJS 读取文件，通过 `column_map` 识别维度列与值列。
- 经营数据范例.xlsx：`公司名` 列 + `月份` 列是维度，其余列是科目值列 → 每个"科目列"对应一个 `account_code`
- 静态数据范例.xlsx：行是科目，列是"4 期间维度 × 10 公司"组合 → 拆解列头得到 `company_code` + `period_dim_code`
- 年度预算范例.xlsx：行是科目，列是 10 家公司 → 拆解列头得到 `company_code`

**Step 4 — Zod 校验**：Zod schema 校验每行数据（校验逻辑收敛到后端单一实现）。

**Step 5 — 行级 unpivot**：对每行数据，遍历所有值列，生成多条长表记录。

**Step 6 — 映射方案 `column_map` JSON 结构示例**：

```json
{
  "data_type": "operating",
  "dimension_columns": {
    "company": {"source": "header", "column": "公司名"},
    "period": {"source": "header", "column": "月份", "transform": "excel_date_to_yyyy_mm"}
  },
  "value_columns": [
    {"source_column": "本月收入", "target_account_code": "OP_02", "period_dim": "ACTUAL_MONTH"},
    {"source_column": "总成本", "target_account_code": "OP_0301", "period_dim": "ACTUAL_MONTH"}
  ]
}
```

**Step 7 — 事务批量落库**：unpivot 后的长表记录批量插入（事务 + 批量），返回标准化结果 `{ batchId, successCount, errorCount, errors: [{row, column, message}] }`。

**静态数据多级列头处理**：静态数据范例.xlsx 列头为"公司+期间维度"两级，`column_map` 需支持 `header_row_index` 配置多级表头合并。

## 十、指标体系

### 10.1 Metric 表结构（详见 8.5 节）

### 10.2 calc 类型特殊字段说明

| 字段 | 类型 | 用途 |
|------|------|------|
| `source_account_codes` | JSONB 数组 | 记录 calc 指标公式引用了哪些 `account_subject.code`（如 `["OP_0401", "OP_0201"]`），建立可追溯链路，便于口径审计与影响分析 |
| `depends_on` | JSONB 数组 | 记录直接依赖的指标 code（如 `["OP_0401", "OP_0201"]`），用于 AggregationService 构建依赖 DAG + 拓扑排序 + 环检测 |

### 10.3 公式引擎规范

**四则运算安全解析**：
- 仅支持白名单字符：`0-9`、`.`、`+`、`-`、`*`、`/`、`(`、`)`、空格
- **禁止 `eval`** — 使用安全表达式解析器（如 `mathjs` 或自定义 parser）
- 操作数引用格式：`{metric_code}`（如 `{OP_025} + {OP_030}`）

**计算流程**：
1. 从 `metric.depends_on` 构建指标依赖 DAG
2. 拓扑排序确定计算顺序
3. **环检测**：发现环报错 `METRIC_CIRCULAR_REF`，拒绝计算
4. 按拓扑序依次计算每个 calc 指标
5. 同比/环比统一由后端 `IndicatorsService` 计算，不存库

### 10.4 汇总映射环检测

- **写入时**：BFS/DFS 环检测，若汇总主体间形成引用环（如 ET0001→ET0002→ET0001），拒绝写入并报错 `AGGREGATION_CIRCULAR_REF`
- **查询时**：递归 CTE 加 `depth` 计数器 + `LIMIT` 防止无限递归

### 10.5 指标生成规则（种子阶段）

种子阶段从 `分析主体及汇总映射.xlsx` Sheet6/8 读取每个科目的数据类型标注：
- `data（数据类）` → `metric.data_type = 'data'`，`metric.code = account_subject.code`
- `calc（计算类）` → `metric.data_type = 'calc'`，`metric.code = 'CALC_' + 业务名`
- `display（展示类）` → `metric.data_type = 'display'`，`metric.code = account_subject.code`

每个 `AccountSubject` 对应一条 `Metric` 记录。Fact 数据生成仅对 `is_leaf=true` 且 `dataType='data'` 的科目生成 mock 事实数据，计算类/展示类指标由 `AggregationService` 实时计算。

- 每列隐含两个维度：科目 + 期间维度（本月实际/同期实际/本年累计/同期累计，通过列名映射区分）

### A.3 `静态数据范例.xlsx` 列结构概要

- 左侧维度列：科目名称（总资产、银行存款、应收账款、存货13种产品明细、负债、权益等）
- 值列（~40列）：10家公司 × 4期间维度（本期金额/年初金额/同期金额/上年年初金额）
- 列头多级：第一级=期间维度，第二级=公司名

### A.4 `年度预算范例.xlsx` 列结构概要

- 左侧维度列：科目名称（回款/收入/成本/毛利/费用/利润/接驳户数/现金流，与经营科目完全对应）
- 值列（~10列）：10家公司，每列=该公司该科目的年度预算金额
- 财年信息从文件名或导入参数获取
