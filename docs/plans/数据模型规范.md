## 一、设计原则

### 1.1 三大范式应用

数据库设计严格遵循三大范式，所有反范式例外均需满足"明确的业务场景 + 严格评估"两个条件。

#### 1NF — 字段原子化

每个字段存储单一、不可分割的值。禁止将多个信息合并到一个字段中。

| 规则 | 违反示例 | 正确做法 |
|------|---------|---------|
| 公司主体编码与名称分离 | `company_info = "CO330059-浙江壹品慧杭州分公司"` | `code = "CO330059"`, `name = "浙江壹品慧杭州分公司"` 分两字段 |
| 期间维度不合并 | `period_info = "2025-06本月实际"` | `period = "2025-06"`, `period_dim_code = "ACTUAL_MONTH"` 分两字段 |
| 汇总映射逗号分隔多值拆为多行 | `single_codes = "CO330059,CO330060,CO330061"` | 在 `company_aggregation_map` 中拆为 3 行，一行一映射关系 |
| 科目列名不编码多义 | 列名 `本月收入` 同时隐含科目和期间维度 | column_map 拆解：`source_column="本月收入" → account_code="OP_025", period_dim="ACTUAL_MONTH"` |

#### 2NF — 消除部分依赖

所有非主键字段必须完全依赖**整个主键**（尤其针对联合主键）。若某字段仅依赖部分主键，应拆分到独立表。

| 规则 | 违反示例 | 正确做法 |
|------|---------|---------|
| 事实表 value 依赖完整复合键 | 若主键含 `company_code` 但 `value` 只依赖 `account_code`，则违反 2NF | `fact_operating` 的 `value` 完全依赖 `(company_code, account_code, period, period_dim_code, batch_id)` 整个复合键 |
| 账龄区间用长表而非宽表 | `aging_record` 宽表设计：`amount_0_1M`, `amount_1_3M`, `amount_3_6M`... 各列仅部分依赖主键 | 长表设计：`(company_code, counterparty_code, account_code, period, bucket_code)` → `amount`，一行一区间 |

#### 3NF — 消除传递依赖

非主键字段之间不能存在传递依赖（即非主键字段不能依赖其他非主键字段）。应拆分为独立表并通过外键关联。

| 规则 | 违反示例 | 正确做法 |
|------|---------|---------|
| 公司名称只存 `company` 表 | 事实表存 `company_name` 字段 → `company_name` 依赖 `company_code`，`company_code` 又依赖主键 | 事实表只存 `company_code` (FK)，名称通过 JOIN `company` 获取 |
| 科目名称只存 `account_subject` 表 | 事实表存 `account_name` 字段 | 事实表只存 `account_code` (FK)，名称通过 JOIN 获取 |
| 期间维度名称只存 `period_dimension` 表 | 事实表存 `period_dim_name` 字段 | 事实表只存 `period_dim_code` (FK) |

**3NF 核心目标**：
- 减少数据冗余 — 同一信息不重复存储
- 保证数据一致性 — 修改一处即可全局生效
- 提升可维护性 — 结构清晰，便于扩展

### 1.2 长表设计策略

**核心问题**：Excel 数据文件是"一行多公司多期间"的**宽表**，数据库 FactRecord 采用**长表**（一行一指标一值）。

**转换策略**：导入时在后端 `ImportService` 执行 **unpivot/melt**（宽表→长表转换），非前端执行。

```
宽表行（Excel）：
{公司:杭州壹品慧, 月份:2025-06, 本月收入:120000, 总成本:80000, ...}

        ↓ ImportService.unpivot()

长表行（数据库）：
{company_code:"CO330059", period:"2025-06", account_code:"OP_025", period_dim_code:"ACTUAL_MONTH", value:120000}
{company_code:"CO330059", period:"2025-06", account_code:"OP_030", period_dim_code:"ACTUAL_MONTH", value:80000}
...
```

### 1.3 三张事实表分离理由

经营数据、静态数据、年度预算来自 3 个不同的 Excel 文件，期间维度体系不同：

| 事实表 | 期间维度体系 | 数据来源 |
|--------|-------------|---------|
| `fact_operating` | 经营 5 个：预算金额、本月实际、同期实际、本年累计、同期累计 | 经营数据数据范例.xlsx |
| `fact_static` | 静态 4 个：本期金额、年初金额、同期金额、上年年初金额 | 静态数据范例.xlsx |
| `fact_budget` | 财年 + 月度/年度 | 年度预算范例.xlsx |

分表存储更清晰，符合 3NF（消除不同期间维度体系的传递依赖）。

### 1.4 软删除查询过滤

所有标记 `status` 字段的表（`company`、`account_subject`、`counterparty`、`user`、`role`、`metric` 等），**业务查询必须过滤 `status = 'active'`**。

- 通过 Prisma 扩展层（`softDelete.ts`）统一注入过滤条件，避免遗漏
- 软删除数据泄漏到查询结果视为 Bug

### 1.5 反范式例外规则

为查询性能可适当冗余，但需满足**两个条件**：
1. 有明确的业务场景驱动
2. 已严格评估必要性及数据不一致风险

**允许的反范式示例**：

| 表 | 字段 | 理由 |
|----|------|------|
| `transaction_detail` | `closing_balance` | 期末余额 = 期初 + 借方 - 贷方，虽可计算，但作为高频查询字段保留。一致性风险可控：单一导入批次内计算确定 |

### 1.6 容量规划

| 指标 | 数值 |
|------|------|
| 经营数据年增量 | ~22 万行/年（10公司 × 12月 × 5期间维度 × ~70科目 × ~5.3） |
| 静态数据年增量 | ~1,360 行/批次（10公司 × 34科目 × 4期间维度） |
| 3 年数据总量 | ~66 万行 |
| 存储空间 | ~108 MB/年（含索引） |
| 单次导入 unpivot 经营数据 | ~18,240 行/批次（10公司 × 12月 × ~152科目） |
| 单次导入 unpivot 静态数据 | ~1,360 行/批次 |

## 二、编码规则

### 2.1 公司编码

| 类型 | 格式 | 示例 | 说明 |
|------|------|------|------|
| **单体公司** | `CO` + 6位数字 | `CO330059`（浙江壹品慧杭州分公司） | 前缀 `CO` 使程序可直接区分单体/汇总，无需查表 |
| **汇总主体** | `SUM` + 4位数字 | `SUM0001`（浙江省公司汇总） | 前缀 `SUM` 使程序可直接区分单体/汇总，无需查表 |

数据来源：`分析主体及汇总映射.xlsx`（10 单体 + 10 汇总）。

### 2.2 科目编码

| 类型 | 格式 | 数量 | 说明 |
|------|------|------|------|
| **经营科目** | `OP_001` ~ `OP_152` | 152项 | 5级层级（level 0-4） |
| **静态科目** | `ST_001` ~ `ST_034` | 34项 | 3级层级（level 0-2） |

**科目分类（category）**：
- 经营科目大类：回款 / 收入 / 成本 / 毛利 / 费用 / 经营指标 / 财务指标 / 现金流指标
- 静态科目大类：资产 / 负债 / 权益

### 2.3 指标编码

| 指标类型（data_type） | 编码规则 | 示例 |
|----------------------|----------|------|
| **data（数据类）** | `metric.code = account_subject.code` | `OP_025`（燃气具-灶具收入） |
| **display（展示类）** | `metric.code = account_subject.code` | 与科目编码一致（分类汇总节点） |
| **calc（计算类）** | `CALC_` + 业务名称 | `CALC_资产负债率`、`CALC_增值业务毛利率` |

**calc 类型特殊字段**：
- `source_account_codes`（JSON 数组）：记录公式引用了哪些 `account_subject.code`，建立可追溯链路
- `depends_on`（JSON 数组）：记录直接依赖的指标 code，用于 DAG 拓扑排序 + 环检测

> calc 指标 code 使用 `CALC_` 前缀命名空间，与 data/display 类型的科目编码严格区分，避免编码冲突。

### 2.4 Resource 三段式编码（权限）

权限表 `permission.resource` 字段采用**三段式 `模块:子页面:操作`** 编码。

| 层级 | 格式 | 示例 | 说明 |
|------|------|------|------|
| **模块级** | `{module}` | `data`、`indicators`、`admin` | 控制整个模块的访问 |
| **页面级** | `{module}:{page}` | `data:import`、`admin:users` | 控制模块内特定页面的访问 |
| **按钮级** | `{module}:{page}:{button}` | `data:import:upload`、`admin:users:reset-password` | 控制页面内特定按钮的可见性与可操作性 |

**action 字段枚举值**：`view` / `create` / `update` / `delete` / `export` / `import`

**完整 resource 编码清单**：

| 模块 | resource 编码 | 适用 action |
|------|--------------|-------------|
| 登录页 | `auth:login` | （公开路由，无需权限校验） |
| 首页看板 | `dashboard:view`、`dashboard:export` | view, export |
| 财务指标 | `indicators:view`、`indicators:export` | view, export |
| 往来分析 | `transactions:view`、`transactions:create`、`transactions:update`、`transactions:delete`、`transactions:import`、`transactions:export` | 全部 |
| 存货管理 | `inventory:view`、`inventory:create`、`inventory:update`、`inventory:delete`、`inventory:import`、`inventory:export` | 全部 |
| 分析报告 | `reports:view`、`reports:create`、`reports:update`、`reports:delete`、`reports:export` | view, create, update, delete, export |
| 数据管理 | `data:browse:view`、`data:import:upload`、`data:metric:create`、`data:metric:update`、`data:metric:delete`、`data:company:create`、`data:company:update`、`data:company:delete`、`data:subject:create`、`data:subject:update`、`data:subject:delete`、`data:export` | 全部 |
| 权限管理 | `admin:users:view`、`admin:users:create`、`admin:users:update`、`admin:users:delete`、`admin:users:reset-password`、`admin:users:export`、`admin:roles:view`、`admin:roles:create`、`admin:roles:update`、`admin:roles:delete`、`admin:permissions:view`、`admin:permissions:update` | 全部 |

## 三、维度表（主数据）

所有维度表数据源自 `分析主体及汇总映射.xlsx`。

### 3.1 公司主体表 `company`

**数据来源**：`分析主体及汇总映射.xlsx` Sheet1（10 单体）+ Sheet2（10 汇总）

| # | 字段 | 类型 | 约束 | 说明 |
|---|------|------|------|------|
| 1 | `id` | UUID | PK | 主键（Prisma: `@id @default(uuid())`） |
| 2 | `code` | VARCHAR | UQ, NOT NULL | 公司编码。单体：`CO`+6位数字（如 `CO330059`）；汇总：`SUM`+4位数字（如 `SUM0001`） |
| 3 | `name` | VARCHAR | NOT NULL | 公司全称 |
| 4 | `entity_type` | ENUM | NOT NULL | `single`（单体公司）/ `summary`（汇总主体） |
| 5 | `legal_entity` | VARCHAR | NULLABLE | 法人实体名称（用于内部抵消，单体公司填写） |
| 6 | `management_entity` | VARCHAR | NULLABLE | 管理主体（管理口径合并范围） |
| 7 | `business_unit` | VARCHAR | NULLABLE | **事业部编码**（如 `BU_EAST`/`BU_WEST`），用于 `org_scope_bu` → `company_code` 映射。scope.ts 解析 org_scope_bu 时查此字段获取 company_code 列表 |
| 8 | `parent_code` | VARCHAR | FK → `company.code` | 汇总主体的上级（汇总主体可嵌套，如"华东区汇总"→"浙江省公司汇总"） |
| 9 | `status` | ENUM | NOT NULL, DEFAULT `'active'` | `active` / `inactive`（软删除标记，所有查询必须过滤 status='active'） |
| 10 | `order_no` | INT | DEFAULT 0 | 排序号 |
| 11 | `created_at` | TIMESTAMP | DEFAULT NOW() | 创建时间 |
| 12 | `updated_at` | TIMESTAMP | DEFAULT NOW() | 更新时间 |
| 13 | `created_by` | VARCHAR | FK → `user.id` | 创建人 |
| 14 | `updated_by` | VARCHAR | FK → `user.id` | 更新人 |

**3NF 说明**：公司名称、法人实体、管理主体等属性只在此表存储一次，事实表通过 `company_code` 外键引用，消除传递依赖。

### 3.2 汇总映射表 `company_aggregation_map`

**数据来源**：`分析主体及汇总映射.xlsx` Sheet3-4（汇总映射关系）。

| # | 字段 | 类型 | 约束 | 说明 |
|---|------|------|------|------|
| 1 | `id` | UUID | PK | 主键 |
| 2 | `summary_company_code` | VARCHAR | FK → `company.code`, NOT NULL | 汇总主体编码（如 `SUM0001`） |
| 3 | `single_company_code` | VARCHAR | FK → `company.code`, NOT NULL | 单体公司编码（如 `CO330059`） |
| 4 | `is_internal_elimination` | BOOLEAN | DEFAULT false | 是否需内部抵消（关联方交易） |
| 5 | `created_at` | TIMESTAMP | DEFAULT NOW() | 创建时间 |
| 6 | `updated_at` | TIMESTAMP | DEFAULT NOW() | 更新时间 |

**唯一约束**：`(summary_company_code, single_company_code)` 唯一。

**环检测说明**：
- **写入时**：BFS/DFS 环检测，若汇总主体间形成引用环（如 SUM0001→SUM0002→SUM0001），拒绝写入并报错 `AGGREGATION_CIRCULAR_REF`
- **查询时**：递归 CTE 加 `depth` 计数器 + `LIMIT` 防止无限递归

**1NF 说明**：Excel Sheet3-4 中单体与汇总映射是逗号分隔多值，seed 导入时需先建立名称→编码映射表，再将映射拆分为多行（一行一映射关系）存入此表。

### 3.3 科目体系表 `account_subject`

**数据来源**：`分析主体及汇总映射.xlsx` Sheet5（经营科目层级，5列=level0~level4）、Sheet6（经营科目类型：数据类/计算类/展示类）、Sheet7（静态科目层级）、Sheet8（静态科目类型）。

| # | 字段 | 类型 | 约束 | 说明 |
|---|------|------|------|------|
| 1 | `id` | UUID | PK | 主键 |
| 2 | `code` | VARCHAR | UQ, NOT NULL | 科目编码。经营：`OP_001`~`OP_152`；静态：`ST_001`~`ST_034` |
| 3 | `name` | VARCHAR | NOT NULL | 科目名称 |
| 4 | `subject_type` | ENUM | NOT NULL | `operating`（经营科目）/ `static`（静态科目） |
| 5 | `level` | INT | NOT NULL | 层级：0-4（经营科目5级）/ 0-2（静态科目3级） |
| 6 | `parent_code` | VARCHAR | FK → `account_subject.code`, NULLABLE | 上级科目编码（根节点为 NULL） |
| 7 | `category` | VARCHAR | NOT NULL | 大类。经营科目大类：回款/收入/成本/毛利/费用/经营指标/财务指标/现金流指标；静态科目大类：资产/负债/权益 |
| 8 | `direction` | ENUM | NOT NULL | `debit`（借方）/ `credit`（贷方） |
| 9 | `is_leaf` | BOOLEAN | NOT NULL | 是否叶子科目（可录入数据的明细科目）。非叶子节点为分类汇总节点 |
| 10 | `status` | ENUM | NOT NULL, DEFAULT `'active'` | `active` / `inactive`（软删除） |
| 11 | `order_no` | INT | DEFAULT 0 | 排序号 |
| 12 | `created_at` | TIMESTAMP | DEFAULT NOW() | 创建时间 |
| 13 | `updated_at` | TIMESTAMP | DEFAULT NOW() | 更新时间 |

**数据量**：152 项经营科目 + 34 项静态科目 = **186 项**（含中间层级节点）。

**层级构建**：从 Excel 层级路径（如 `["收入","壹品慧收入","增值业务收入","厨房产品销售收入","燃气具-灶具收入"]`）解析父子关系，自动填充 `parent_code`、`level`、`is_leaf`。

## 四、事实表（核心业务数据）

### 4.1 经营数据事实表 `fact_operating`

**数据来源**：`经营数据数据范例.xlsx`（140行 × 21列）。

| # | 字段 | 类型 | 约束 | 说明 |
|---|------|------|------|------|
| 1 | `id` | UUID | PK | 主键 |
| 2 | `batch_id` | UUID | FK → `import_batch.id`, NOT NULL | 导入批次 |

### 4.4 宽表→长表转换策略（ImportService 7 步流程）

转换流程在后端 `ImportService` 中执行（非前端）。

**Step 1 — 接收原始文件**：multer 接收 FormData 上传的原始 .xlsx 文件，校验 MIME magic number + fileSize ≤ 50MB。

**Step 2 — 识别映射方案**：根据 `data_type` 查询 `mapping_scheme` 表，获取 `column_map` JSON 配置。

**Step 3 — 流式解析**：SheetJS/ExcelJS 读取文件，通过 `column_map` 识别维度列与值列。
- 经营数据范例.xlsx：`公司名` 列 + `月份` 列是维度，其余列是科目值列 → 每个"科目列"对应一个 `account_code`
- 静态数据范例.xlsx：行是科目，列是"4 期间维度 × 10 公司"组合 → 拆解列头得到 `company_code` + `period_dim_code`
- 年度预算范例.xlsx：行是科目，列是 10 家公司 → 拆解列头得到 `company_code`

**Step 4 — Zod 校验**：Zod schema 校验每行数据（校验逻辑收敛到后端单一实现）。

**Step 5 — 行级 unpivot**：对每行数据，遍历所有值列，生成多条长表记录。

**Step 6 — 映射方案 `column_map` JSON 结构示例**：

```json
{
  "data_type": "operating",
  "dimension_columns": {
    "company": {"source": "header", "column": "公司名"},
    "period": {"source": "header", "column": "月份", "transform": "excel_date_to_yyyy_mm"}
  },
  "value_columns": [
    {"source_column": "本月收入", "target_account_code": "OP_025", "period_dim": "ACTUAL_MONTH"},
    {"source_column": "总成本", "target_account_code": "OP_030", "period_dim": "ACTUAL_MONTH"}
  ]
}
```

**Step 7 — 事务批量落库**：unpivot 后的长表记录批量插入（事务 + 批量），返回标准化结果 `{ batchId, successCount, errorCount, errors: [{row, column, message}] }`。

**静态数据多级列头处理**：静态数据范例.xlsx 列头为"公司+期间维度"两级，`column_map` 需支持 `header_row_index` 配置多级表头合并。

## 八、指标体系

### 8.1 Metric 表结构（详见 7.5 节）

### 8.2 calc 类型特殊字段说明

| 字段 | 类型 | 用途 |
|------|------|------|
| `source_account_codes` | JSONB 数组 | 记录 calc 指标公式引用了哪些 `account_subject.code`（如 `["OP_025", "OP_030"]`），建立可追溯链路，便于口径审计与影响分析 |
| `depends_on` | JSONB 数组 | 记录直接依赖的指标 code（如 `["OP_025", "OP_030"]`），用于 AggregationService 构建依赖 DAG + 拓扑排序 + 环检测 |

### 8.3 公式引擎规范

**四则运算安全解析**：
- 仅支持白名单字符：`0-9`、`.`、`+`、`-`、`*`、`/`、`(`、`)`、空格
- **禁止 `eval`** — 使用安全表达式解析器（如 `mathjs` 或自定义 parser）
- 操作数引用格式：`{metric_code}`（如 `{OP_025} + {OP_030}`）

**计算流程**：
1. 从 `metric.depends_on` 构建指标依赖 DAG
2. 拓扑排序确定计算顺序
3. **环检测**：发现环报错 `METRIC_CIRCULAR_REF`，拒绝计算
4. 按拓扑序依次计算每个 calc 指标
5. 同比/环比统一由后端 `IndicatorsService` 计算，不存库

### 8.4 汇总映射环检测

- **写入时**：BFS/DFS 环检测，若汇总主体间形成引用环（如 SUM0001→SUM0002→SUM0001），拒绝写入并报错 `AGGREGATION_CIRCULAR_REF`
- **查询时**：递归 CTE 加 `depth` 计数器 + `LIMIT` 防止无限递归

### 8.5 指标生成规则（种子阶段）

种子阶段从 `分析主体及汇总映射.xlsx` Sheet6/8 读取每个科目的数据类型标注：
- `data（数据类）` → `metric.data_type = 'data'`，`metric.code = account_subject.code`
- `calc（计算类）` → `metric.data_type = 'calc'`，`metric.code = 'CALC_' + 业务名`
- `display（展示类）` → `metric.data_type = 'display'`，`metric.code = account_subject.code`

每个 `AccountSubject` 对应一条 `Metric` 记录。Fact 数据生成仅对 `is_leaf=true` 且 `dataType='data'` 的科目生成 mock 事实数据，计算类/展示类指标由 `AggregationService` 实时计算。
