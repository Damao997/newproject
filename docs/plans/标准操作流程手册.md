## 2. 开发新功能（标准流程）

### 2.1 前置：从最新 develop 派生分支

```powershell
# 在开发目录 D:\flies\pj3
git checkout develop
git pull origin develop
git checkout -b feat/<简短英文描述> develop   # 如 feat/import-coverage-optimize
```

**验证点**：`git branch --show-current` 显示 `feat/xxx`。

### 2.2 启动开发环境三服务

| 服务 | 启动方式 | 端口 |
|------|----------|------|
| 开发数据库 | `cd server && npm run db:local`（嵌入式 PG，数据目录 server/.pgdata） | 5432 |
| 后端 | `cd server && npm run dev`（tsx watch） | 3001 |
| 前端 | `cd web && npm run dev`（vite，代理 /api/v1 → 3001） | 5173 |

**验证点**：浏览器打开 `http://localhost:5173` 可登录；`http://localhost:3001/health` 返回 service up + db up。

### 2.3 开发与本地验证（质量门禁）

提交前必须全部通过（server 与 web 各自执行）：

```powershell
cd D:\flies\pj3\server
npm run typecheck        # TypeScript 类型检查
npm run lint             # ESLint 检查
npm run test             # 单元测试（vitest）

cd D:\flies\pj3\web
npm run typecheck        # 若 web 有此脚本，否则 npx tsc -b
npm run lint
npm run test
```

涉及数据库结构变更时额外执行：
```powershell
cd D:\flies\pj3\server
npx prisma migrate dev --name <迁移描述>   # 生成迁移并在开发库应用
npx prisma generate                        # 重新生成 Prisma Client
```

**验证点**：typecheck 0 错误、lint 0 错误、测试全绿；涉及数据模型变更时开发库已应用新迁移。

### 2.4 提交代码

```powershell
git add <变更文件>
git commit -m "feat: <简体中文描述>"
```

- pre-commit 钩子自动执行 lint-staged（只检查暂存文件）
- 提交信息遵循 Conventional Commits：`feat / fix / refactor / docs / style / test / chore` + 中文描述
- 一个提交只做一件事（原子提交）；复杂任务拆多个提交

### 2.5 推送与合回 develop

```powershell
git push origin feat/xxx
```

然后 GitHub 网页创建 PR（feat/xxx → develop），合并进 develop。合并后删除远程分支与本地分支：

```powershell
git checkout develop && git pull origin develop
git branch -d feat/xxx
```

**验证点**：develop 已包含新功能代码，本地工作区干净（`git status`）。

## 3. 修复 Bug

### 3.1 普通 Bug（非紧急）

流程与开发新功能完全相同（§2），分支前缀用 `fix/`：

```powershell
git checkout develop && git pull
git checkout -b fix/<简短描述> develop
# 修复 → 验证门禁（§2.3）→ 提交 → 推送 → PR 合并回 develop
```

### 3.2 生产紧急 Bug（hotfix）

| 对比项 | 普通修复 | hotfix |
|--------|----------|--------|
| 分支起点 | develop | **main** |
| 合并目标 | develop | **main 与 develop 两路** |
| 发布紧迫度 | 随下次发布 | 立即发布（§5 全流程） |

操作：

```powershell
# 1. 从 main（当前生产代码）派生
git checkout main && git pull
git checkout -b hotfix/<简短描述> main

# 2. 修复 + 验证门禁（§2.3）+ 提交 + 推送
git push origin hotfix/<简短描述>

# 3. 分别合并两条路（GitHub 两个 PR）：
#    PR-1: hotfix/xxx → main（修复生产）
#    PR-2: hotfix/xxx → develop（防止下次发布覆盖修复）

# 4. 立即发布（见 §5，从"打 tag"步骤开始）
```

**验证点**：修复同时存在于 main 与 develop；生产已部署新 tag。

## 4. 代码提交与分支管理

### 4.1 提交规范速查

| 类型 | 使用场景 | 示例 |
|------|----------|------|
| `feat` | 新功能 | `feat: 添加经营数据批量导入` |
| `fix` | Bug 修复 | `fix: 修复 JWT 过期未返回 401` |
| `refactor` | 重构（无行为变化） | `refactor: 拆分导入服务` |
| `docs` | 文档变更 | `docs: 更新环境管理规范` |
| `style` | 样式/格式 | `style: 统一表格行高` |
| `test` | 测试相关 | `test: 补充导入边界用例` |
| `chore` | 构建/依赖/工具 | `chore: 升级 prisma 版本` |

### 4.2 本地钩子（提交与推送时自动执行）

| 钩子 | 触发时机 | 行为 | 放行方法 |
|------|----------|------|----------|
| pre-commit | `git commit` | lint-staged 检查暂存文件，失败则提交被拒 | 修复问题后重试（不要跳过） |
| pre-push | `git push` | 拦截 `refs/heads/main` 直推（生产分支保护） | `ZJYPH_ALLOW_MAIN_PUSH=1 git push origin main`（不推荐，仅应急） |

### 4.3 分支生命周期

```
main（生产）←─────── PR 合并（发布）────── develop（开发集成）
  │                                                ↑
  └── hotfix/*（应急，双路合回）              feat/*、fix/*（短期，合完即删）
```

- 禁止直接推送 main（钩子拦截）；正常路径 = PR 网页合并
- 分支命名：`feat/`、`fix/`、`refactor/`、`hotfix/` + 英文简短描述

## 5. 生产发布流程（端到端）

> 完整发布共 5 步。前 3 步约 5 分钟，第 4 步由 deploy 脚本自动完成（约 5-10 分钟），第 5 步为发布后确认。

### 步骤 1：develop 合并进 main

GitHub 网页创建 PR（develop → main）并合并。合并后本地同步：

```powershell
git checkout main && git pull origin main
git checkout develop && git pull origin develop
```

**验证点**：GitHub 上 main 分支头部 = 待发布提交。

### 步骤 2：打发布标签

```powershell
git tag v2026.08.2          # 序号递增（v2026.08.1 → v2026.08.2）
git push origin v2026.08.2
```

**验证点**：`git tag -l` 看到新 tag；`git ls-remote --tags origin` 远程可见。

### 步骤 3：生产目录检出 tag

```powershell
cd D:\ZJYPH-prod
git fetch --tags
git checkout v2026.08.2
```

**验证点**：`git describe --tags` 输出 v2026.08.2。

### 步骤 4：一键部署

```powershell
# 内网访问场景必须带 -ApiBaseUrl（用服务器内网 IP，不能用 localhost——否则内网其他机器
# 的浏览器会把 localhost 解析成访问者自己的电脑，导致"网络连接异常"）
powershell -ExecutionPolicy Bypass -File server\scripts\deploy-zjyph.ps1 -Tag v2026.08.2 -ApiBaseUrl http://192.168.1.43:3100/api/v1
```

脚本自动执行六步 checklist（任一步失败即中止）：

| 步骤 | 内容 | 失败处理 |
|------|------|----------|
| 0/6 | 前置检查（.env、node_modules） | 按提示补齐后重跑 |
| 1/6 | 发布前全量备份 + 自校验 | 备份失败 → 中止发布，先修复备份 |
| 2/6 | prisma migrate deploy（超级用户） | 迁移失败 → 中止，按 §8 场景 B 处理 |
| 3/6 | 构建后端 + 前端（注入 API 地址与版本标识） | 构建失败 → 修复代码后重新发布 |
| 4/6 | 重启 zjyph-backend / zjyph-frontend | 重启后自动进入健康检查 |
| 5/6 | 健康检查（/health + 前端 8080） | 失败自动重试 10 次，仍失败则中止 |
| 6/6 | 冒烟验证（5 项全绿） | 未通过 → 中止发布 |

**验证点**：脚本末尾显示"部署完成 ✔"与"当前部署：v2026.08.2"。

### 步骤 5：发布后确认

```powershell
# 1. 巡检一遍（进程/健康/磁盘/备份时效/连接数）
powershell -ExecutionPolicy Bypass -File server\scripts\ops-check-zjyph.ps1

# 2. 浏览器访问 http://localhost:8080 并登录验证核心功能
# 3. 查看页面版本标识（<meta name="app-version">）确认为 v2026.08.2
```

**发布窗口约定**：非工作时间发布（避开使用高峰）。

### 6.1 脚本总览

| zjyph-ecosystem.config.cjs | server/ | PM2 三进程配置 |

### 6.2 deploy-zjyph.ps1（发布）

```powershell
# 常规发布（推荐，会自动检出 tag；-ApiBaseUrl 用服务器内网 IP 192.168.1.43）
powershell -ExecutionPolicy Bypass -File server\scripts\deploy-zjyph.ps1 -Tag v2026.08.2 -ApiBaseUrl http://192.168.1.43:3100/api/v1

# 参数
#   -Tag <tag>      要部署的 tag（留空则用当前检出状态）
#   -ApiBaseUrl     前端 API 地址（内网访问必须用服务器内网 IP；本机访问可用 http://localhost:3100/api/v1）
#   -SkipBackup     跳过发布前备份（仅演练，不推荐）
#   -SkipSmoke      跳过冒烟（仅演练，不推荐）
```

前置条件：生产 `server\.env` 已配置；备份密钥环境变量 `ZJYPH_BACKUP_KEY` 可用。

### 6.3 backup-zjyph.ps1（备份/恢复）

```powershell
# 全量备份（每日计划任务执行此项）
powershell -ExecutionPolicy Bypass -File server\scripts\backup-zjyph.ps1 -Action full
# 输出示例：[2026-08-07 15:50:14] 全量备份完成：zjyph_prod_20260807_155014.dump.enc（2.74 MB）
#          [2026-08-07 15:50:14] 新备份校验通过

# 校验备份可解密且结构完整
powershell -ExecutionPolicy Bypass -File server\scripts\backup-zjyph.ps1 -Action verify -BackupFile D:\ZJYPH-backup\full\<文件>

# 恢复（破坏性！双重确认：-ConfirmRestore 参数 + 交互输入 yes；恢复前自动做保护性备份）
powershell -ExecutionPolicy Bypass -File server\scripts\backup-zjyph.ps1 -Action restore -BackupFile D:\ZJYPH-backup\full\<文件> -ConfirmRestore

# 清理 30 天前旧备份（full 动作自动执行，也可手动）
powershell -ExecutionPolicy Bypass -File server\scripts\backup-zjyph.ps1 -Action cleanup
```

- 连接参数自动从生产 `server\.env` 的 MIGRATE_DATABASE_URL 解析，无需手工设置环境变量
- 需要环境变量：`ZJYPH_BACKUP_KEY`（备份加密密钥，已存入用户环境变量）
- 备份产物：`D:\ZJYPH-backup\full\zjyph_prod_<时间戳>.dump.enc`

### 6.4 ops-check-zjyph.ps1（巡检，建议每周）

```powershell
powershell -ExecutionPolicy Bypass -File server\scripts\ops-check-zjyph.ps1
# 检查项：PM2 三进程 / /health / 前端 8080 / 磁盘空间 / 备份时效 / 数据库连接数
# 退出码：0 = 正常；1 = 存在异常（可在计划任务中用于告警）
```

### 6.5 production-smoke-zjyph.ps1（冒烟，发布后自动执行）

```powershell
powershell -ExecutionPolicy Bypass -File server\scripts\production-smoke-zjyph.ps1
# 5 项：/health、前端 200、未授权 401、登录失败 401、审计落库（UTC 时区比较）
# 全绿输出"冒烟验证全部通过"，退出码 0
```

### 6.6 数据库相关

```powershell
# 生产 PG 实例（PM2 托管，一般不需要手动执行）
cd D:\ZJYPH-prod\server && npm run db:prod

# 生产库账号权限初始化（幂等；新库首次部署时执行）
```

## 7. 数据流向与隔离机制

### 7.1 数据流向图

```
【生产环境】                                  【开发环境】
Excel 导入 → 生产后端(3100)                  Excel 导入 → 开发后端(3001)
         → zjyph_prod 库(5433)                        → yipinhui_finance 库(5432)
              │                                          │
              │ 每日 02:00 备份                            │（开发数据随意增删，不影响生产）
              ▼                                          │
   D:\ZJYPH-backup\*.dump.enc（AES-256 加密）             │
              │                                          │
              └── 恢复（restore）→ zjyph_prod             │
                                                         │
  一次性迁移：migrate-data.mjs 开发库 ─────────→ 生产库
```

### 7.2 隔离边界清单（8 重隔离）

| 边界 | 开发 | 生产 |
|------|------|------|
| 代码目录 | D:\flies\pj3（develop 分支） | D:\ZJYPH-prod（只跟 tag） |
| 数据库实例 | embedded PG（server/.pgdata，5432） | embedded PG（D:\ZJYPH-data，5433，仅回环） |
| 数据库名 | yipinhui_finance | zjyph_prod |
| 数据库账号 | postgres（开发固定密码） | postgres（随机强密码）+ zjyph_app（仅 DML） |
| 后端端口 | 3001 | 3100 |
| 前端端口 | 5173（vite dev） | 8080（静态托管） |
| 环境变量 | server/.env（开发） | server/.env（生产，独立，icacls 收紧） |
| 日志/备份 | 终端输出 | D:\ZJYPH-prod\logs + D:\ZJYPH-backup |

### 7.3 允许跨环境流动的数据

| 流动方向 | 方式 | 时机 |
|----------|------|------|
| 开发库 → 生产库（一次性全量） | migrate-data.mjs | 生产库首次建立/重建时 |
| 生产库 → 加密备份 → 生产库 | backup-zjyph.ps1（full/restore） | 每日备份 / 灾难恢复 |
| 代码 → 生产 | git tag + checkout + deploy | 每次发布 |

**禁止**：开发环境直接连生产库；生产环境执行开发脚本（cleanup-test-data 等）；把开发 .env 复制到生产。

## 8. 异常情况回滚与恢复

### 场景 A：发布后代码问题（功能异常）

```
症状：发布后页面/接口异常，冒烟未覆盖到
处置：
  1. cd D:\ZJYPH-prod && git checkout <上一tag>   # 回到上一个好版本
  2. powershell -ExecutionPolicy Bypass -File server\scripts\deploy-zjyph.ps1
     # 自动完成备份 → 迁移（无新迁移）→ 构建 → 重启 → 健康检查 → 冒烟
  3. 确认 /health 与页面恢复正常
注意事项：若上一版本代码与当前数据库 schema 不兼容（本次发布含迁移），
         需先评估是否同时恢复备份（见场景 B）
```

### 场景 B：发布后数据问题（迁移损坏 / 数据异常）

```
症状：发布后数据查询报错、数据被迁移破坏
处置：
  1. 先恢复备份（恢复 = 覆盖生产库，双重确认）：
     powershell -ExecutionPolicy Bypass -File server\scripts\backup-zjyph.ps1 `
       -Action restore -BackupFile D:\ZJYPH-backup\full\<发布前备份> -ConfirmRestore
     # 输入 yes 确认；脚本先自动做保护性备份再恢复
  2. 回滚代码到与备份一致的版本（发布前 tag）：
     cd D:\ZJYPH-prod && git checkout <发布前tag>
  3. 重新执行 deploy 脚本（跳过备份步骤以节省时间：-SkipBackup；但仅限此场景）
  4. 验证：登录、数据查询、巡检
红线：恢复是破坏性操作，恢复前自动留保护性备份；恢复后立即验证
```

### 场景 C：生产 PG 意外退出（端口 5433 拒连）

```
症状：/health 返回 db down；Test-NetConnection 127.0.0.1 5433 失败；应用报连接拒绝
诊断：
  1. pm2 status                                  # zjyph-postgres 状态（注意：可能显示 online 但实际已死，属 stale）
  2. Get-Process postgres | 查看是否有 -D D:\ZJYPH-data 的主进程
  3. Get-Content D:\ZJYPH-prod\logs\postgres.err.log -Tail 20   # 崩溃原因
处置（干净重启）：
  pm2 delete zjyph-postgres
  cd D:\ZJYPH-prod\server
  pm2 start zjyph-ecosystem.config.cjs --only zjyph-postgres
  pm2 save
验证：Test-NetConnection 127.0.0.1 -Port 5433；/health 返回 db up
备注：若存在孤儿 postgres 子进程（父进程已死），按父进程链识别后清理
```

### 场景 D：备份失败或校验失败

```
症状：backup 输出"备份失败"或"新备份校验失败，请立即人工介入"
排查：
  1. ZJYPH_BACKUP_KEY 是否变更（setx 查看；变更会导致旧备份无法解密）
  2. 磁盘空间（D 盘；巡检第 3 项）
  3. 备份文件权限（icacls D:\ZJYPH-backup\full\<文件>；应仅当前用户）
  4. 生产 PG 是否在线（场景 C）
处置：修复后重新执行 -Action full；校验通过才算备份成功
```

### 场景 E：磁盘空间告警 / 日志增长

```
症状：巡检报告磁盘剩余 <10GB；或 D:\ZJYPH-prod\logs 增长过快
处置：
  1. 检查备份目录占用（保留 30 天的策略是否生效）
  2. pm2-logrotate 配置确认：pm2 conf pm2-logrotate（max_size=10M、retain=30）
  3. 清理临时文件（%TEMP%、安装器残留如 D:\ZJYPH-tools\pg15.zip）
  4. 必要时手动触发日志轮转：pm2 trigger pm2-logrotate rotate
```

### 场景 F：登录异常 / 限流误伤

```
症状：正常用户被限流（429）、登录失败
排查：
  1. 限流阈值：5 次/分钟（middleware/rate-limit），等待 1 分钟自动恢复
  2. 审计日志确认是否有人尝试暴力登录：psql 查 audit_log 的 login_failed 高频记录
  3. 检查 FRONTEND_ORIGIN 是否包含访问来源（内网 IP 访问需在白名单）
```
