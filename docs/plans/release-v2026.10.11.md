# v2026.10.11 首页指标双模式、导入按公司整月替换与部署管线修复

发布日期：2026-10-08。上一稳定版本：v2026.10.9。变更分类：用户可感知的功能（首页指标口径切换）、用户可感知的行为调整（导入激活覆盖范围）、以及运维缺陷修复（部署管线 Prisma 生成）。

本版为**合并批次**：v2026.10.10 已创建正式 tag 但**从未部署**（原因见下），其用户可见内容随本版一并上线，对外公告条目也合并到 v2026.10.11。

## 发布范围

1. **首页核心指标双模式（月度 / 财年累计）**：新增个人偏好 `dashboardKpiMode`（`month` | `ytd`，默认 `month`），前后端 schema、类型与偏好存储同步；设置页「使用习惯」新增口径切换项，随账号跨设备同步。月度口径展示本月实际与环比，累计口径展示财年累计与累计同比。
2. **指标卡补充环比与累计同比**：`Kpi` 新增 `ytdYoy`、`monthMom` 与 `monthMomReason`；`kpiMonthComparison` 把「上月无数据」与「上月基数为 0」分别标注（前端用气泡说明原因），不再伪装成持平。`hasOperatingData` 按当前授权主体判断上月是否有数据，避免其他公司有数据时把本主体缺失误判为零。
3. **导入激活改为按「公司 × 月份」整月替换**：月度报表（经营/静态/现金流）激活覆盖粒度由「按期间合并」改为按文件实际出现的（公司 × 月份）组合整月替换——未包含的公司与月份继续保留，同公司同月未包含的旧科目一并替换。新增 `server/src/lib/import-coverage.ts`（静态表按 UTC 自然月半开区间匹配，空组合返回 `OR: []` 不匹配任何旧数据）；预览、备份、批量冲突检查与回滚统一使用同一组合口径。
4. **导入覆盖范围预览**：前端新增 `MonthlyActivationImpact` 组件，展示「将新增 / 将替换 / 继续保留」的公司月份组合及整月替换说明；预算类型仍走财年整体替换提示。批量激活文案与 `import-boundary` 文档口径由「三元组」统一为「同类型组合」。
5. **重分类失效判断改用 `withoutScope`** 读取事实真值，避免把操作者作用域外的其他公司行误判为已删除。
6. **更新公告未知类型崩溃修复（v2026.10.10 内容）**：`NOTE_TYPE_META` 正式纳入 `note`，并新增 `noteMeta(type)` 兜底——映射表外的公告类型回落「更新」标签，人工维护的公告数据出现新类型不再崩溃整页；含两例回归测试。
7. **部署管线 Prisma 生成修复（运维缺陷）**：`server/package.json` 增加 `postinstall: prisma generate`（同时覆盖 dev 与 CI）；`deploy-zjyph.ps1` 在后端 `npm ci` 之后、`tsc` 之前**显式**执行 `prisma generate` 并断言退出码，不再依赖 `@prisma/client` 的生命周期钩子。

## v2026.10.10 部署失败与恢复（复盘）

**现象**：2026-10-08 16:47 部署 v2026.10.10，全量备份成功后，检出 tag、后端 `npm ci` 成功，随后 `tsc` 报 **496 条**缺类型错误、构建中止。

**根因**：后端 `npm ci` 之后 `node_modules/.prisma/client/index.d.ts` 只有 **3989 字节**的占位桩（正常应为 2.5 MB），即 Prisma Client 未被生成。`tsc` 因此报 `@prisma/client has no exported member …` 一片错误。经隔离目录实测，`npm ci` 在该环境**可以**正常触发 `@prisma/client` 的 postinstall 并生成客户端，故判定为「管线依赖生命周期钩子生成」这一不可靠设计，而非环境或代码缺陷。

**影响扩大**：脚本的失败回退在依赖已被 `npm ci` 替换之后重载 PM2，后端 `new PrismaClient()` 撞上桩文件抛错（`logs/backend.err.log` 有明文 `@prisma/client did not initialize yet`），连续崩溃 16 次被 PM2 标记 `errored`。**生产 API 不可用约 5 分钟（16:47–16:53）**，前端静态页仍返回 200。

**恢复（手工干预，事后说明）**：在生产目录执行 `prisma generate` 生成客户端 → `pm2 restart zjyph-backend` → 把生产 `HEAD` 恢复到与实际运行产物一致的 `v2026.10.9`。恢复后巡检全绿、冒烟 5/5 PASS。该次手工干预只涉及 `node_modules` 内的生成产物与 tag 检出（与部署脚本自身动作一致），未覆盖 `web/dist`。

**残留风险（未在本版消除）**：部署脚本的失败回退路径会在依赖已替换后重载进程，理论上仍可能把「构建失败」放大为「服务不可用」。后续可考虑改为仅在产物已切换时才重载进程。
