# 环境管理规范：开发与生产环境分离

> 文档定位：**权威深度规范**（docs/plans/）。本文件是浙江壹品慧财年经营数据分析平台"开发与生产环境分离"体系的总纲，完整记录分支管理、物理隔离、数据库分离、部署流程、安全措施与运维规范。所有内容均基于 2026-08-07 已落地的实际配置，与 `docs/references/vcs.md`（版本控制规范）、`docs/references/devops.md`（部署运维规范）配合使用，冲突时以本文件为准。

## 1. 概述

### 1.1 背景与目标

改造前，项目存在三层混用：

| 问题 | 表现 | 风险 |
|------|------|------|
| 代码版本混用 | 所有开发提交直接落在 `main`，无发布 tag | 生产无法独立控制发布节奏，开发中的代码可能被部署 |
| 文件夹混用 | 生产与开发共用 `D:\flies\pj3` | git 操作原地替换运行中进程的文件；未验证代码被误部署 |
| 数据库混用 | 生产真实数据与开发测试数据共用同一 PostgreSQL 实例（`server/.pgdata`） | 测试数据污染生产；迁移互相影响；误删即真删 |

改造目标：版本可控、环境隔离、运维完备、可回滚。

### 1.2 方案演进

- **Docker 规划（未启用）**：仓库内已有完整 Docker 资产（`docker-compose.yml` 四服务、`backup.sh`、`.env.example`、`init-roles.sql`、`nginx.conf`），但生产实际未使用容器。
- **当前落地（2026-08-07）**：内网单机、非 Docker，采用"独立目录 + 双嵌入式 PG 实例 + PM2 托管 + 脚本固化"方案，把 Docker 资产的设计精华（最小权限、备份加密、健康检查、端口最小暴露）以原生方式移植落地。
- **未来演进**：Docker 资产保留为迁移路径，见 §12。

### 1.3 环境总览

```
开发环境（D:\flies\pj3）              生产环境（ZJYPH，D 盘独立目录）
┌────────────────────────────┐      ┌──────────────────────────────────┐
│ 前端 dev 5173（vite proxy）│      │ 前端 8080（serve-static.cjs）     │
│ 后端 dev 3001（tsx watch） │      │ 后端 3100（dist/src/server.js）   │
│ PG 5432（server/.pgdata）  │      │ PG 5433（D:\ZJYPH-data）          │
│ 代码：main/develop 分支    │      │ 代码：D:\ZJYPH-prod（只跟 tag）   │
└────────────────────────────┘      └──────────────────────────────────┘
```

## 2. 总体架构

### 2.1 生产资源命名规范（ZJYPH-）

所有生产资源统一以 `ZJYPH-`（浙江壹品慧）为前缀，与开发环境（pj3）从名称上彻底区分：

| 资源 | 命名 | 说明 |
|------|------|------|
| 生产代码目录 | `D:\ZJYPH-prod` | git 检出 tag，严禁开发操作 |
| 生产数据目录 | `D:\ZJYPH-data` | 嵌入式 PG 数据文件 |
| 生产备份目录 | `D:\ZJYPH-backup` | 加密备份（full/ + logs/） |
| 生产日志目录 | `D:\ZJYPH-prod\logs` | pm2-logrotate 轮转 |
| 生产工具目录 | `D:\ZJYPH-tools` | PostgreSQL 官方工具（pg_dump/psql/pg_restore） |
| 生产数据库 | `zjyph_prod` | 与开发库 `yipinhui_finance` 隔离 |
| 业务账号 | `zjyph_app` | 仅 DML，无 DDL |
| PM2 进程 | `zjyph-postgres` / `zjyph-backend` / `zjyph-frontend` | 三进程托管 |
| 备份计划任务 | `ZJYPH-backup-daily` | 每日 02:00 |

> ⚠️ **红线（2026-08-10 事故后强化）**：在 `D:\ZJYPH-prod` 生产目录下**严禁**执行任何开发数据库命令：
> `npm run db:local`、`npm run setup`、`npm run prisma:migrate`（dev 版）、`npm run prisma:seed`、`rmdir /s /q server\.pgdata`。
> 误执行 `db:local` 会在生产目录新建孤立的空数据实例（`server\.pgdata`，端口 5432），与生产库（5433）隔离、不损坏生产数据，但会造成"数据丢失"假象并干扰排障。
> 生产数据库管理**仅允许**：PM2 启停（zjyph-postgres）、`npm run db:prod`、`deploy-zjyph.ps1` 部署、`backup-zjyph.ps1` 备份/恢复、`prisma migrate deploy` 迁移。
> 开发命令一律在 `D:\flies\pj3` 下执行。`local-db.ts` 已内置 NODE_ENV=production 拒绝启动防护（2026-08-10 新增）。

### 2.2 端口与进程矩阵

| 服务 | 开发 | 生产 | 生产监听 | 生产进程 |
|------|------|------|----------|----------|
| PostgreSQL | 5432 | 5433 | 仅 127.0.0.1 | zjyph-postgres |
| 后端 API | 3001 | 3100 | 全部接口（防火墙限定） | zjyph-backend |
| 前端 | 5173 | 8080 | 全部接口（防火墙限定） | zjyph-frontend |

### 2.3 关键决策记录

| 决策 | 理由 |
|------|------|
| 生产用嵌入式 PG 第二实例（同款 embedded-postgres） | 零额外安装、与开发机制一致；数据目录/端口/库名全隔离 |
| 备份加密用 .NET AES-256 而非 openssl | Windows 无 openssl；PowerShell 原生实现，自洽 |
| 前端静态托管自研 `serve-static.cjs` 而非 serve 包 | serve 参数解析不可靠（实测 bug），自研 30 行零依赖、SPA fallback 可控 |
| main 保护用本地 pre-push 钩子 | GitHub 免费个人账户私有仓库不强制执行 rulesets/分支保护（付费墙），钩子在本机等效拦截 |
| 迁移脚本按"列交集"迁移 | 开发库存在未提交的 schema 漂移（如 deleted_at），生产基线保持纯净 |

## 3. 分支管理策略（Git Flow 精简版）

### 3.1 分支模型

```
main（生产，受保护，部署基准 = 生产目录只检出 tag）
  ├── develop（开发集成）
  │     ├── feat/xxx、fix/xxx、refactor/xxx（短期分支，合并后删除）
  │     └── hotfix/xxx（从 main 派生，修复后分别合回 main 与 develop）
```

| 分支 | 职责 | 保护 |
|------|------|------|
| `main` | 生产就绪代码，唯一部署来源 | 本地 pre-push 钩子拦截直推；GitHub 侧付费墙说明见 §3.3 |
| `develop` | 日常开发集成 | 无 |
| `feat/*` `fix/*` `refactor/*` | 单个功能/修复，短期存活 | 无 |
| `hotfix/*` | 生产紧急修复 | 无 |

### 3.2 发布标签

- 格式：`v<年>.<月>.<序号>`（如 `v2026.08.1`、`v2026.08.2`）
- 基线：`v2026.08.1`（2026-08-07，提交 c4bcf25，当前生产版本）
- 打标签命令：`git tag v2026.08.x && git push origin v2026.08.x`

### 3.3 main 保护机制（重要）

**事实**：GitHub 免费个人账户的私有仓库**不强制执行** rulesets 与经典分支保护（"Your rulesets won't be enforced on this private repository until you move to GitHub Team organization account"），配置后也不拦截直推。

**当前方案**：本地 pre-push 钩子（`.husky/pre-push`）在推送侧拦截：
- `git push origin main` → 拒绝，提示走 PR
- 临时放行（不推荐）：sh 语法 `ZJYPH_ALLOW_MAIN_PUSH=1 git push origin main`；Windows PowerShell 为 `$env:ZJYPH_ALLOW_MAIN_PUSH=1; git push origin main`（完成后 `Remove-Item Env:ZJYPH_ALLOW_MAIN_PUSH`）
- 正常发布路径（develop → PR 网页合并进 main）不受影响

**升级路径**（团队协作时）：GitHub Pro（$4/月）获得经典分支保护；或 Team 组织（$4/用户/月）获得 rulesets 强制。升级后钩子保留作双保险。

### 3.4 工作流

| 场景 | 操作 |
|------|------|
| 日常开发 | `git checkout -b feat/xxx develop` → 开发验证（typecheck + lint + test）→ 合并回 develop |
| 发布 | develop → GitHub PR 合并进 main → 打 tag → 生产目录检出 tag → 跑部署脚本（§6） |
| 紧急修复 | `git checkout -b hotfix/xxx main` → 修复 → 分别合回 main 与 develop |
| 提交规范 | Conventional Commits（feat/fix/refactor/docs/style/test/chore），见 `docs/references/vcs.md` |

## 4. 环境物理隔离

### 4.1 目录布局

```
开发环境（保持现状）              生产环境（本次建立）
D:\flies\pj3                      D:\ZJYPH-prod     生产代码（只跟 tag）
  └─ server\.pgdata（开发库）       ├─ server\       后端（.env 生产专用）
                                    ├─ web\          前端
                                    └─ logs\         生产日志
                                  D:\ZJYPH-data      生产 PG 数据目录
                                  D:\ZJYPH-backup    加密备份
                                  D:\ZJYPH-tools     PG 官方工具
```

**铁律**：
- 生产目录只执行 `git fetch` → `git checkout <tag>` → `npm ci` → 部署脚本
- 严禁在生产目录切换分支或 pull 未发布代码
- 生产 `.env` 与开发 `.env` 完全独立，互不覆盖，均不进 git
- 生产目录已配置 **git sparse-checkout**（cone 模式，仅检出 `server/` 与 `web/`）：docs/、.qoder/ 等文档类文件不进入生产工作区；运行必需文件（deploy/backup 脚本、prisma migrations、生产 .env、ecosystem 配置、serve-static.cjs）全部在保留目录内，不受影响。需查阅 docs 时用 `git show v2026.08.x:docs/references/devops.md` 或直接在开发目录 `D:\flies\pj3` 查看

### 4.2 前端 API 地址

- 生产前端构建时注入 `VITE_API_BASE_URL`（web 代码读取该变量，默认 `/api/v1`）
- **本机访问**：构建为 `http://localhost:3100/api/v1`
- **内网访问**：必须构建为 `http://192.168.1.43:3100/api/v1`（服务器内网 IP）——不能用 localhost，否则内网其他机器的浏览器会把 localhost 解析成访问者自己的电脑导致"网络连接异常"；同时后端 `FRONTEND_ORIGIN` 白名单需包含 `http://192.168.1.43:8080`，防火墙需放行 3100
- 发布命令统一带 `-ApiBaseUrl http://192.168.1.43:3100/api/v1`（见标准操作流程手册 §5）；服务器内网 IP 变更时需重新构建并同步 CORS 与防火墙

## 5. 数据库分离配置

### 5.1 双嵌入式 PG 实例

| 项 | 开发实例 | 生产实例 |
|----|----------|----------|
| 启动脚本 | `server/scripts/local-db.ts` | `server/scripts/prod-db.ts` |
| 数据目录 | `server/.pgdata` | `D:\ZJYPH-data` |
| 端口 | 5432 | 5433（仅回环） |
| 数据库 | `yipinhui_finance` | `zjyph_prod` |
| 超级用户 | postgres/postgres（开发固定） | postgres（随机强密码，存生产 .env） |
| 业务账号 | — | `zjyph_app`（仅 DML） |

生产实例配置（`prod-db.ts` 读取生产 `server/.env`）：
```
ZJYPH_DATA_DIR=D:\ZJYPH-data
ZJYPH_PG_PORT=5433
ZJYPH_DB_NAME=zjyph_prod
ZJYPH_PG_PASSWORD=<随机强密码>
```

### 5.2 账号与权限（最小权限原则）

- 业务账号 `zjyph_app`：应用运行时连接（DATABASE_URL），**仅 DML**（SELECT/INSERT/UPDATE/DELETE），无 DDL、无 TRUNCATE/REFERENCES/TRIGGER；audit_log 与 token_blacklist 仅 INSERT + SELECT（防篡改）
- 超级用户 postgres：仅迁移（`prisma migrate deploy`）与备份使用（MIGRATE_DATABASE_URL）
- 权限初始化脚本：`server/scripts/init-zjyph-roles.mjs`（基于 `prisma/init-roles.sql` 参数化，幂等）

### 5.3 数据迁移（开发库 → 生产库）

工具：`server/scripts/migrate-data.mjs`（pg-copy-streams，零外部依赖）：
- 逐表 `COPY` 流式迁移，目标会话 `SET session_replication_role = replica` 绕过外键顺序
- **按"源表与目标表的列交集"迁移**：容忍开发库 schema 漂移，未提交开发的列数据不进生产基线
- `--truncate-target`：迁移前清空目标业务表，保证可重复全量迁移
- 序列自动同步（`setval`）；不迁移 `_prisma_migrations`（保留生产库自身迁移记录）

2026-08-07 首次迁移：43 张表全部完成（user=9、company=23、metric=186、fact_operating=6529、fact_budget=5602、transaction_detail=19265 等）。

### 5.4 时区注意事项（踩坑）

`created_at` 等字段为**无时区 timestamp 列**（Prisma 按 UTC 写入）。用 psql 手工比较时间时必须强制会话时区为 UTC：
```powershell
$env:PGOPTIONS = '-c timezone=UTC'
```
否则列值被按本地时区（Asia/Shanghai）解释，时间比较偏差 8 小时（生产冒烟脚本的审计检查即因此修复）。

## 6. 部署流程

### 6.1 发布 checklist（deploy 脚本固化）

`server/scripts/deploy-zjyph.ps1` 一键执行六步：

```
0/6 前置检查（.env、node_modules 就绪；可选 -Tag 检出）
1/6 发布前全量备份（backup-zjyph.ps1，产出加密备份并自校验）
2/6 数据库迁移（prisma migrate deploy，超级用户连接串）
3/6 构建后端（tsc）+ 前端（vite，注入 VITE_API_BASE_URL 与版本标识）
4/6 重启 zjyph-backend / zjyph-frontend
5/6 健康检查（/health + 前端 8080）
6/6 冒烟验证（production-smoke-zjyph.ps1）
```

### 6.2 常规发布操作

```powershell
# 1. develop 经 PR 合并进 main
git tag v2026.08.x && git push origin v2026.08.x

# 2. 生产目录更新
cd D:\ZJYPH-prod
git fetch --tags
git checkout v2026.08.x

# 3. 一键部署（需备份密钥环境变量）
powershell -ExecutionPolicy Bypass -File server\scripts\deploy-zjyph.ps1 -Tag v2026.08.x
```

### 6.3 首次部署（新机器）步骤

1. `git clone https://github.com/Damao997/FY200.git D:\ZJYPH-prod` → `git checkout <tag>` → 三处 `npm ci`
2. 配置生产 `server\.env`（从 `.env.example` 生成全部密钥；JWT 双密钥 openssl rand -hex 64；数据库密码 ≥12 字符字母数字）
3. 启动生产 PG：PM2 启动 `zjyph-postgres`（首次自动初始化数据目录与 zjyph_prod 库）
4. `npx prisma migrate deploy`（生产库建表）
5. 权限初始化：`node scripts/init-zjyph-roles.mjs`
6. 数据迁移（如从旧库搬迁）：`node scripts/migrate-data.mjs --source <旧库URL> --target <生产URL> --truncate-target`
7. 构建 + PM2 启动三进程 → 冒烟验证

### 6.4 回滚手册

| 场景 | 操作 |
|------|------|
| 代码回滚 | `cd D:\ZJYPH-prod && git checkout <上一tag>` → 重新跑 deploy 脚本 |
| 数据回滚 | 先恢复备份（§7.3），再回滚代码到与备份一致的版本 |
| 版本标识 | 前端页面 `<meta name="app-version">` 可查当前线上版本 |

## 7. 备份与恢复

### 7.1 备份链路

`server/scripts/backup-zjyph.ps1`（Windows 原生实现）：

| 动作 | 说明 |
|------|------|
| `-Action full` | pg_dump -Fc（超级用户）→ AES-256 加密（.NET，密钥 = 环境变量 `ZJYPH_BACKUP_KEY`）→ `D:\ZJYPH-backup\full\zjyph_prod_<时间戳>.dump.enc` → 立即自校验 → 清理 30 天前旧备份 |
| `-Action verify -BackupFile <文件>` | 解密 + pg_restore --list 结构校验（先解密到临时文件，因 --list 只读 TOC 即退出） |
| `-Action restore -BackupFile <文件> -ConfirmRestore` | 双重确认 → 先做保护性备份 → 解密管道 pg_restore --clean 恢复 |
| `-Action cleanup` | 清理过期备份 |

- 连接参数自动从生产 `server\.env` 的 `MIGRATE_DATABASE_URL` 解析（计划任务场景免设环境变量）
- 备份文件权限：icacls 移除继承、仅当前用户可读写

### 7.2 定时任务

```
计划任务：ZJYPH-backup-daily（每日 02:00）
命令：powershell -NoProfile -ExecutionPolicy Bypass -File D:\ZJYPH-prod\server\scripts\backup-zjyph.ps1 -Action full
创建：schtasks /create /tn "ZJYPH-backup-daily" /tr "powershell -NoProfile -ExecutionPolicy Bypass -File D:\ZJYPH-prod\server\scripts\backup-zjyph.ps1 -Action full" /sc daily /st 02:00 /f
```

### 7.3 密钥管理（安全红线）

- 备份加密密钥 `ZJYPH_BACKUP_KEY`（≥32 字符，当前为 64 位 hex）已存入用户环境变量，**必须另存到密码管理器单独保管**
- 密钥与备份文件分离存放；丢失密钥 = 历史备份全部无法解密
- 生产 `server\.env` 含全部生产密钥，icacls 已收紧为仅当前用户可读，严禁提交 git

## 8. 安全措施

### 8.1 已落地清单

| 措施 | 实现 |
|------|------|
| 端口最小暴露 | 防火墙放行入站 8080（前端）与 3100（后端，内网访问必需）；数据库 5433 不对外（PG 配置 listen_addresses=127.0.0.1）。权威口径见 §4.2 与 docs/references/devops.md §安全基线 |

| 登录防护 | 登录限流（5 次/分钟）默认启用 |
| 审计 | audit_log 全量记录（含登录成功/失败），业务账号对审计表仅 INSERT+SELECT |
| main 保护 | pre-push 钩子拦截直推（§3.3） |
| 依赖固定 | 生产一律 `npm ci`；`.nvmrc` 固定 Node 20（与 Docker 对齐） |

```powershell
netsh advfirewall firewall add rule name="ZJYPH-api-3100" dir=in action=allow protocol=TCP localport=3100
```

## 9. 运维规范

### 9.1 进程托管（PM2）

- 配置：`server/zjyph-ecosystem.config.cjs`（三进程：postgres/backend/frontend）
- 开机自启：`pm2 save` + `pm2-windows-startup`（注册表 HKCU Run；`pm2 startup` 在 Windows 不可用）
- 日志：`D:\ZJYPH-prod\logs\`，pm2-logrotate（10MB/保留 30 天）
- 常用命令：`pm2 status`、`pm2 logs <name> --lines 50`、`pm2 restart <name>`、`pm2 save`

### 9.2 巡检（每周）

`server/scripts/ops-check-zjyph.ps1`：PM2 三进程状态、/health、前端 8080、磁盘空间（<10GB 告警）、备份时效（>30 小时告警）、数据库连接数。关键项失败退出码非 0。

### 9.3 冒烟（发布后）

`server/scripts/production-smoke-zjyph.ps1`：/health、前端 200、未授权 401、登录失败 401、审计落库（UTC 时区比较）。全绿退出码 0。

### 9.4 故障排查速查

| 症状 | 排查路径 |
|------|----------|
| 5433 拒连 | `pm2 status` 检查 zjyph-postgres；`Get-Process postgres` 找 -D D:\ZJYPH-data 主进程；`pm2 delete zjyph-postgres` 后重新 `pm2 start`（PM2 状态可能 stale） |
| 前端 8080 打不开 | `pm2 logs zjyph-frontend`；确认 `web\dist` 存在；防火墙规则 |
| 后端 /health db down | 检查生产 PG 与 zjyph_app 账号；`server\.env` 的 DATABASE_URL |
| 备份校验失败 | 检查 `ZJYPH_BACKUP_KEY` 是否变化；备份文件 ACL（icacls 查看） |
| 脚本中文乱码/语法错 | PS 5.1 需 UTF-8 **带 BOM** 的 .ps1；脚本已按此规范保存 |

## 10. 实施记录与经验教训（2026-08-07）

| # | 发现 | 处理 |
|---|------|------|
| 1 | `npm run build` 产物在 `dist/src/server.js`（tsconfig rootDir="."），而 start 脚本与 Dockerfile 写 `dist/server.js` —— 既有 bug，Docker 启用必挂 | 修复三处（package.json start、Dockerfile CMD、ecosystem script） |
| 2 | embedded-postgres 包不含 pg_dump/psql 客户端工具 | 安装官方 PostgreSQL 17.10（与生产实例同版本，pg_dump 向后兼容约束） |
| 3 | pg-copy-streams 的 `to()` 是 COPY TO 读流、`from()` 是 COPY FROM 写流（命名反直觉） | 迁移脚本按此修正 |
| 4 | pg_restore --list 只读 TOC 即退出，stdin 管道 CopyTo 造成死锁/异常 | verify 改为先解密到临时文件 |
| 5 | .NET `SetAccessRuleProtection(true,false)` 清空 ACL 导致备份文件不可读 | 改用 `icacls /inheritance:r /grant:r` |
| 6 | serve 包参数解析 bug（`--spa` 被当主机名） | 自研 `serve-static.cjs`（30 行零依赖） |
| 7 | PowerShell 5.1 不支持 `??` 空合并；ConvertFrom-Json 遇大小写重复键报错 | 脚本按 PS 5.1 兼容写法；pm2 状态改文本解析 |
| 8 | 中文 .ps1 需 UTF-8 BOM 否则 PS 5.1 乱码语法错 | 全部脚本统一 BOM |
| 9 | 无时区 timestamp 列的 8 小时时区偏差 | psql 会话 `PGOPTIONS='-c timezone=UTC'` |
| 10 | 开发库存在未提交 schema 漂移（deleted_at 等），生产基线纯净 | 迁移按列交集处理 |

## 11. 常用命令速查

```powershell
# 生产服务
pm2 status                                          # 查看三进程
pm2 logs zjyph-backend --lines 50                   # 后端日志
pm2 restart zjyph-backend                           # 重启后端
pm2 save                                            # 保存进程列表（改动后必做）

# 部署/发布
git tag v2026.08.x && git push origin v2026.08.x    # 打发布标签
cd D:\ZJYPH-prod && git fetch --tags && git checkout v2026.08.x
powershell -ExecutionPolicy Bypass -File server\scripts\deploy-zjyph.ps1 -Tag v2026.08.x

# 备份
powershell -ExecutionPolicy Bypass -File server\scripts\backup-zjyph.ps1 -Action full
powershell -ExecutionPolicy Bypass -File server\scripts\backup-zjyph.ps1 -Action verify -BackupFile <文件>

# 巡检/冒烟
powershell -ExecutionPolicy Bypass -File server\scripts\ops-check-zjyph.ps1
powershell -ExecutionPolicy Bypass -File server\scripts\production-smoke-zjyph.ps1

# 数据库
powershell -ExecutionPolicy Bypass -File server\scripts\backup-zjyph.ps1 -Action restore -BackupFile <文件> -ConfirmRestore
& D:\ZJYPH-tools\pgsql\bin\psql.exe -h 127.0.0.1 -p 5433 -U postgres -d zjyph_prod   # 生产库 psql
```
