# 生产部署与发布流程（生产唯一入口）

> 文档定位：**生产上线唯一操作流程**。凡涉及 `main`、正式 tag、生产部署、回滚或生产运行时变更，Agent 和维护人员必须先阅读本文件，并以仓库中的发布脚本实际校验结果为准。
>
> 适用环境：Windows 内网非 Docker 生产环境。开发目录为 `D:\ZJYPHFA-dev`，生产目录为 `D:\ZJYPHFA`。生产运行时数据、真实 `.env`、备份、PG 工具和运行时配置只存在于生产目录，不进入 Git 提交。

## 1. 发布原则与不可违反的边界

1. **生产只部署正式 tag**。正式 tag 必须是带注释 tag，格式为 `vYYYY.MM.N`，且 tag 的提交必须属于远端 `origin/main`。
2. **代码只在开发目录修改**。所有编码、测试、提交、推送和 PR 操作在 `D:\ZJYPHFA-dev` 完成；`D:\ZJYPHFA` 只执行获取 tag、备份、部署、巡检和回滚。
3. **生产禁止就地 stash**。禁止在 `D:\ZJYPHFA` 执行 `git stash`、`git stash -u`、`git stash -a`、`git pull`、切换开发分支或开发数据库命令。
4. **发布前必须备份**。正式 tag 发布不允许使用 `-SkipBackup`；备份失败必须中止发布。
5. **发布后必须验证**。正式 tag 发布不允许使用 `-SkipSmoke`；健康检查和冒烟失败时不得手工覆盖生产文件。
6. **不绕过发布脚本**。生产唯一部署入口是 `server/scripts/deploy-zjyph.ps1`。`-AllowUntagged` 只允许本地演练，禁止用于正式生产。

如果任一前置条件不满足，立即停止发布并报告阻塞原因，不得通过删除文件、清空数据目录、跳过备份或强制重启来“排障”。

## 2. 角色与目录职责

| 目录 | 角色 | 允许操作 |
|---|---|---|
| `D:\ZJYPHFA-dev` | 开发/发布准备 | 拉取、建分支、编码、测试、提交、推送、创建 PR、创建 tag |
| `D:\ZJYPHFA` | 生产运行 | 获取 tag、发布前备份、部署、健康检查、冒烟、回滚 |

生产运行资产包括：

- `D:\ZJYPHFA\data`：生产 PostgreSQL 数据目录；
- `D:\ZJYPHFA\backup`：加密数据库备份；
- `D:\ZJYPHFA\tools`：PostgreSQL 官方客户端工具；
- `D:\ZJYPHFA\server\.env`：生产密钥与连接串；
- `D:\ZJYPHFA\ops-panel\runtime-config.json`：生产端口和运行时配置；
- `D:\ZJYPHFA\logs`、PM2 进程和 `web\.release`：运行时日志与发布暂存产物。

这些内容不得通过 `git add`、`git stash` 或人工复制带入开发分支。

## 3. 正式发布前：开发目录操作

### 3.1 更新与验证

```powershell
cd D:\ZJYPHFA-dev
git fetch origin --prune --tags
git switch develop
git pull --ff-only origin develop
git switch -c feat/<简短名称>
```

完成修改后，必须在开发目录执行：

```powershell
npm run verify
git status --short
git diff --check
```

暂存时使用明确文件列表，禁止 `git add .`：

```powershell
git add <明确的文件列表>
git commit -m "feat: 简体中文说明"
git push -u origin feat/<简短名称>
```

### 3.2 PR 合并门禁

1. 通过 PR 将 `develop` 合入 `main`；生产紧急修复从 `main` 创建 `hotfix/*`，合入 `main` 后必须同步回 `develop`。
2. 等待 CI 的 `verify` 检查成功，不得在 CI 运行中合并，不得以本地通过替代远端 CI。
3. 合并前确认 PR 的目标是 `main`、工作树无未提交改动、没有把真实配置或运行数据纳入提交。
4. 记录合并提交 SHA，后续 tag 必须指向合并后的 `main`。

### 3.3 创建正式 tag

在已更新到远端 `main`、且工作树干净的开发目录执行：

```powershell
cd D:\ZJYPHFA-dev
git fetch origin --prune --tags
git log -1 --oneline origin/main
git status --short
git tag -a v2026.09.3 -m "release: v2026.09.3"
git push origin v2026.09.3
```

`v2026.09.3` 仅为示例，必须替换为尚未存在的下一个版本号。创建后核验：

```powershell
git cat-file -t v2026.09.3
git merge-base --is-ancestor "v2026.09.3^{commit}" origin/main
git show --no-patch --format=fuller v2026.09.3
```

只有同时满足以下条件才允许进入生产目录：tag 存在于远端、tag 类型为 `tag`、tag 提交属于 `origin/main`、CI 已通过。

## 4. 生产目录正式部署

### 4.1 发布前只读确认

```powershell
cd D:\ZJYPHFA
git status --short --untracked-files=no
git fetch origin --prune --tags
pm2 status
powershell -NoProfile -ExecutionPolicy Bypass -File server\scripts\ops-check-zjyph.ps1
```

生产工作区不得存在已跟踪文件改动或暂存改动。运行时目录出现的未跟踪 `data`、`backup`、`tools`、`recovery-*` 等属于生产资产，不得删除或 stash。

### 4.2 唯一部署入口

```powershell
cd D:\ZJYPHFA
powershell -NoProfile -ExecutionPolicy Bypass -File server\scripts\deploy-zjyph.ps1 -Tag v2026.09.3
```

正式发布不得附带以下参数：

- `-AllowUntagged`：仅本地演练使用；
- `-SkipBackup`：正式发布禁止跳过发布前备份；
- `-SkipSmoke`：正式发布禁止跳过冒烟验证。

### 4.3 部署脚本执行顺序

`deploy-zjyph.ps1` 会按以下顺序执行，并在任一步失败时终止：

1. **前置检查**：确认生产 `.env`、`ZJYPH_DATA_DIR`、PG_VERSION、运行时端口、PM2 和工作树状态；校验 tag 格式、注释类型及其属于 `origin/main`。
2. **发布前全量备份**：调用 `backup-zjyph.ps1 -Action full`，生成加密备份并立即校验。
3. **检出正式 tag**：生产目录 detached HEAD 精确检出目标 tag，不切换到 `main` 或 `develop`。
4. **安装与构建**：后端、前端均使用 `npm ci`；前端先构建到 `web\.release\dist-next`，不直接覆盖当前线上 `web\dist`。
5. **数据库迁移**：使用生产超级用户迁移连接串执行 `prisma migrate deploy`。
6. **切换产物与重载**：迁移成功后才切换前端静态产物，并仅重载 `zjyph-backend`、`zjyph-frontend`；不重启生产 PostgreSQL。
7. **健康检查与冒烟**：检查后端 `/health`、数据库状态、前端 HTTP 200、同源 `/api/v1` 代理和生产冒烟场景。

## 5. 发布后验收与记录

部署命令成功后，在生产目录再次执行：

```powershell
cd D:\ZJYPHFA
git describe --tags --exact-match
git status --short --untracked-files=no
powershell -NoProfile -ExecutionPolicy Bypass -File server\scripts\ops-check-zjyph.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File server\scripts\production-smoke-zjyph.ps1
pm2 status
```

验收记录至少包含：

- 发布 tag、合并提交 SHA、部署时间；
- 发布前备份文件名和校验结果；
- `/health`、前端 8080、同源 API 代理和冒烟结果；
- 数据库迁移结果及 PM2 重启次数；
- 若失败，记录失败步骤、日志路径和回滚动作。

发布成功后，生产目录的 `HEAD` 必须精确匹配正式 tag。生产工作区允许存在运行时未跟踪目录，但不允许存在已跟踪文件漂移。

## 6. 失败处理与回滚

### 6.1 部署中止

若备份、构建、迁移、静态切换或冒烟失败：

1. 保留 `logs`、备份文件和终端错误信息；
2. 不要手工覆盖 `web\dist`，不要删除 `web\.release\dist-previous`；
3. 确认 PM2、后端 `/health` 和数据库状态；
4. 在开发目录定位根因，修复后通过新 PR 和新 tag 重新发布。

### 6.2 代码回滚

代码回滚仍通过同一个部署入口，目标为上一稳定 tag：

```powershell
cd D:\ZJYPHFA
powershell -NoProfile -ExecutionPolicy Bypass -File server\scripts\deploy-zjyph.ps1 -Tag <上一稳定tag>
```

### 6.3 数据回滚

若迁移包含不可逆变化，不能只回退代码。必须先根据发布记录选择与目标版本匹配的加密备份，再按恢复流程执行保护性备份、确认和恢复：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File server\scripts\backup-zjyph.ps1 -Action restore -BackupFile <已验证备份文件> -ConfirmRestore
```

数据恢复属于高风险操作，执行前必须明确确认目标库、备份文件和恢复窗口；禁止用开发库覆盖生产库。

## 7. Agent 发版协议

Agent 接到“发布、上线、部署、打 tag、回滚生产”等请求时，必须按以下顺序执行：

1. 先读取根 `CLAUDE.md`、本文件和 `docs/plans/环境管理规范.md`；
2. 确认当前操作目录，生产操作只能在 `D:\ZJYPHFA`，开发操作只能在 `D:\ZJYPHFA-dev`；
3. 在生产发布前核对 PR、CI、正式 tag、备份密钥、生产数据目录和工作树状态；
4. 只调用 `deploy-zjyph.ps1 -Tag <正式tag>`，不得自行拼接替代流程；
5. 每一步如实报告结果，遇到失败、数据目录异常、工作树漂移或 tag 校验失败立即停止；
6. 发布结束后执行巡检与冒烟，并报告实际版本、备份文件和健康结果；
7. 用户未明确授权时，不得推送、合并、打 tag、恢复数据库或删除恢复资产。
