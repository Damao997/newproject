# 浙江壹品慧财财年经营数据分析 Web 平台 — 整合方案可行性审查报告

**审查人**：架构师 高见远
**审查对象**：《浙江壹品慧财年经营数据分析 Web 平台 — 整合方案》
**审查维度**：前端设计规范 / 后端设计规范 / 数据库规范 / Agent 约束
**审查日期**：2026-07-10

## 一、总体评估

> **一句话结论**：方案整体架构方向正确、技术选型务实、模块划分合理，可在修订 P0 阻断项后进入开发；但存在若干"设计意图与工程落地之间的裂缝"（前端大文件解析、AI 脱敏过激导致分析失真、双套公司编码、批次膨胀无治理），需在动工前修复，否则会在中期返工。

### 可行性评分

| 维度 | 评分 | 简评 |
|---|---|---|
| 前端设计规范 | **7.5 / 10** | 技术栈选型合理，但 SheetJS 大文件解析、Tailwind+AntD 冲突、i18n 仅是"口头预留"未落地 |
| 后端设计规范 | **7.0 / 10** | 11 Service 划分清晰，但前后端双层校验冗余、公式引擎缺环检测、SSE 反代配置需显式声明 |
| 数据库规范 | **7.5 / 10** | 三范式意识到位，但双套公司编码、batch_id 唯一约束致数据膨胀、string FK 性能隐患 |
| Agent/AI 约束 | **7.0 / 10** | AIProxyService 统一出口架构正确，但金额脱敏不可逆将严重削弱"AI 追加分析"价值 |
| **综合** | **7.3 / 10** | 修订 P0 后可进入开发 |

| # | 检查点 | 问题描述 | 风险等级 | 改进建议 |
|---|---|---|---|---|
| F-R-1 | **AntD ProTable 未显式声明** | 方案称"Ant Design 5 的 Table/ProTable 能力强"，但 ProTable 来自独立包 `@ant-design/pro-components`，与 `antd` 主体包分离。方案依赖列表中未列出该包，工程师可能误以为 antd 自带。 | 中 | 在 Required Packages 中显式添加 `@ant-design/pro-components@^2.x`，并注明 ProTable 的虚拟滚动需 `scroll.y` + `pagination={false}` 配合，否则虚拟滚动不生效。 |
| F-R-2 | **Tailwind CSS + AntD 样式冲突** | Tailwind 的 `preflight`（CSS Reset）会重置 AntD 的全局样式（按钮边框、表格边框等），导致组件视觉异常。方案未提及此冲突的处理方案。 | 中 | 在 `tailwind.config.ts` 中设置 `corePlugins: { preflight: false }`，或仅对 AntD 无法覆盖的布局区域使用 Tailwind utility class，避免全局 reset。需在 T01 基础设施任务中验证。 |
| F-R-3 | **SSE 流式写入 TipTap 的交互设计** | 方案提到 `/reports/{id}/ai/polish(SSE)` 流式润色，但未描述流式文本如何渐进写入编辑器的交互方案。直接流式插入会导致光标跳动、已编辑内容被覆盖。 | 中 | 明确交互模式：①"选中段落→AI 润色→流式预览→用户确认替换"模式（推荐），或 ②"全文润色→新开 diff 视图→用户逐段接受"。不要直接流式覆盖编辑器内容。 |
| F-R-4 | **数值色标与 i18n 预留的矛盾** | "正数红色 / 负数绿色"是中国市场惯例，但与西方惯例完全相反。方案声称"i18n/多币种预留"，但若色标逻辑硬编码，后续国际化需推翻重写。 | 低 | 将色标方向抽为 `localeConfig.colorDirection: 'cn' | 'intl'`，formatMoney 函数接收 locale 参数。当前固定 `'cn'` 即可，但接口要预留。 |
| F-R-5 | **前端解析 vs 服务端解析切换的架构预留不充分** | 方案称"预留切换"，但 MVP 全程依赖前端 SheetJS 解析。切换到服务端解析意味着前端发送原始文件（FormData）而非解析后 JSON，后端 ImportService 的数据结构需同时兼容两种输入。方案未定义切换的接口契约。 | 中 | 定义统一的 `ImportPayload` 类型（无论来源均为标准化行数组），前端解析路径和后端解析路径都输出该类型。切换时只需改 `parseLocation: 'client' | 'server'` 配置开关。 |

#### ❌ 问题项

| # | 检查点 | 问题描述 | 风险等级 | 改进建议 |
|---|---|---|---|---|
| F-P-1 | **SheetJS 前端解析 >20MB 文件不可行** | 方案第四章明确"导入时执行宽表→长表转换"在前端完成。SheetJS 社区版（xlsx）解析 20MB+ xlsx 文件时，内存峰值可达 200-400MB（xlsx 是 ZIP 压缩 XML，解压后膨胀 10-20 倍），浏览器主线程会冻结 5-15 秒，UI 完全无响应。多级表头（静态数据 42 列）进一步加剧。Web Worker 可缓解 UI 冻结但无法解决内存上限问题。 | **高** | **直接采用服务端解析作为默认路径**：前端上传原始文件 → multer 接收 → 后端 SheetJS/ExcelJS 流式解析 → 返回标准化行数组。前端仅做轻量预览（首 100 行）。这消除了"切换预留"的复杂度，且后端解析可复用校验逻辑。若必须保留前端预览，用 SheetJS `read(data, {sheetRows: 100})` 仅读首 100 行。 |
| F-P-2 | **i18n 预留是"口头承诺"而非架构设计** | 方案反复声称"i18n/多币种预留"，但全文未出现任何 i18n 实际机制：无 i18next / react-i18next 依赖、无 locale context 设计、无文案抽取方案、数值单位硬编码"万"、日期格式硬编码。这不是"预留"，是"未做"。 | 中 | 要么删掉"i18n 预留"的表述（诚实声明 MVP 仅中文），要么至少在 T01 中引入 i18next 骨架 + `useTranslation` 包裹所有硬编码文案 + formatMoney 接收 locale。不要用"预留"掩盖"未设计"。 |

### 维度二：后端设计规范可行性

#### ✅ 合规项

| # | 检查点 | 评估 |
|---|---|---|
| B-OK-1 | **11 Service 划分合理性** | 按业务域划分（Auth/Import/Mapping/Metric/Aggregation/Report/Alert/Transaction/Inventory/ReportAI/Collection）边界清晰。Metric（定义）与 Aggregation（计算）分离，保障了"派生指标计算唯一来源"原则。 |
| B-OK-2 | **公式解析引擎禁 eval 白名单** | 采用四则运算白名单解释器（递归下降 / shunting-yard 算法）替代 eval，安全姿态正确。这是金融系统的必备安全基线。 |
| B-OK-3 | **batch_id 事务原子性** | 每批次一个 batch_id，唯一约束含 batch_id，支持整批提交/回滚。导入失败时整批废弃，不会污染已有数据。设计合理。 |
| B-OK-4 | **RESTful + 统一响应格式** | `/api/v1/*` 版本化前缀 + `{code, data, message}` 统一响应体。虽非严格 REST（code:0 而非纯 HTTP 状态码），但对内部系统而言一致性比教条更重要。 |
| B-OK-5 | **scope.ts 数据权限中间件** | 按事业部（org_scope_bu）注入数据范围，在中间件层统一拦截，业务 Service 无需重复编写权限过滤。模式成熟。 |

#### ⚠️ 风险项

| # | 检查点 | 问题描述 | 风险等级 | 改进建议 |
|---|---|---|---|---|
| B-R-1 | **公式引擎缺依赖环检测** | 方案声明"派生指标计算唯一来源（metric.formula + AggregationService）"，但未提及计算类指标（data_type=calc）可引用其他 calc 指标。若 metric A 引用 metric B，B 又引用 A，将形成无限递归。 | 高 | AggregationService 计算前需构建指标依赖图（DAG），执行拓扑排序检测环。发现环时拒绝计算并报错 `METRIC_CIRCULAR_REF`。在 Metric 表新增 `depends_on` 字段（JSON 数组）记录直接依赖，便于预检。 |
| B-R-2 | **前后端双层 Excel 校验冗余** | 方案要求"前端 SheetJS 校验 + 后端二次校验"。若前端已解析为 JSON 发送，后端需重新实现一遍相同的校验规则（列映射、类型转换、必填检查）。两套校验逻辑极易不一致，维护成本翻倍。 | 中 | 若采纳 F-P-1 建议（服务端解析为默认路径），则校验逻辑自然收敛到后端单一实现，前端仅做格式预检（文件类型/大小）。消除双层校验的同步负担。 |
| B-R-3 | **SSE 在 Express + nginx 下的配置未声明** | 方案列出 SSE 接口（`/reports/{id}/ai/polish(SSE)`）但未提及 nginx 反代的必要配置。默认 nginx 会缓冲 SSE 响应（proxy_buffering on），导致前端收不到流式数据，直到响应结束才一次性返回——SSE 退化为普通请求。 | 中 | 在部署文档中显式声明 nginx 配置：`proxy_buffering off; proxy_cache off; proxy_read_timeout 300s;`，并设置 `X-Accel-Buffering: no` 响应头。Express 端禁用 compression 中间件对 SSE 路由的压缩。 |
| B-R-4 | **JWT 注销无法真正失效** | 方案有 `/auth/logout` 接口，但 JWT 是无状态的，服务端无法主动使其失效（除非维护黑名单）。用户注销后 token 仍有效至过期。内部系统风险可控但需知晓。 | 低 | 采用短期 access token（15min）+ 长期 refresh token（7day）方案。logout 时将 refresh token 加入 Redis/内存黑名单。MVP 阶段可接受"注销仅清前端 token"的简化方案，但需在文档中标注为已知限制。 |
| B-R-5 | **Express 4/5 版本未定** | 方案写"Express 4/5"，未明确选定版本。Express 5 仍处于不稳定阶段（路由 API 变更、中间件签名调整），混用会导致兼容问题。 | 低 | 明确选定 Express 4.18+（LTS），在 package.json 中锁定。待 Express 5 正式 release 后再评估升级。 |
| B-R-6 | **multer 安全边界未量化** | 方案提到 multer 但未指定文件类型白名单、大小上限、并发上传限制。无限制的文件上传是 DoS 攻击面。 | 中 | 配置：`fileFilter` 仅允许 `.xlsx/.xls`；`limits.fileSize = 50 * 1024 * 1024`（50MB）；前端限制同时只允许一个上传任务。后端校验 MIME magic number 而非仅扩展名。 |
| B-R-7 | **派生指标计算无缓存策略** | AggregationService 每次请求都重新计算公式，无缓存。看板首页聚合多公司多指标时，重复计算开销大。 | 低 | 引入计算结果缓存：以 `(metric_code, company_code, period, batch_id)` 为 key 缓存计算结果。batch_id 不变时缓存有效；新批次导入时失效相关缓存。MVP 可不做，但接口预留。 |

#### ❌ 问题项

| # | 检查点 | 问题描述 | 风险等级 | 改进建议 |
|---|---|---|---|---|
| B-P-1 | **SQLite 并发写入限制未评估** | SQLite 是单写入者模型（WAL 模式下读写可并发，但写仍串行）。方案 MVP 用 SQLite，但未评估并发导入场景。若多个用户同时导入 Excel（每个导入是长事务），写锁竞争会导致 `SQLITE_BUSY` 错误，导入失败。 | **高** | ① 启用 WAL 模式：`PRAGMA journal_mode=WAL;`；② 设置 busy_timeout：`PRAGMA busy_timeout=5000;`；③ 导入任务加分布式锁（内存级互斥，同一 data_type 同时只允许一个导入）；④ 文档明确标注 SQLite 仅支持低并发（<5 并发写），高并发需切 PostgreSQL。 |
| B-P-2 | **Prisma + SQLite → PostgreSQL 迁移成本被低估** | 方案称"Prisma 抽象数据库，迁移成本低"。实际上：(1) SQLite 的 JSON 操作用 `json_extract()`，PostgreSQL 用 `->>`/`->`，Prisma 不抽象 JSON 查询语法；(2) SQLite 递归 CTE 与 PostgreSQL 递归 CTE 语法有差异；(3) Prisma 的 SQLite provider 不支持部分 PostgreSQL 特性（如数组字段、enum）；(4) 数据迁移需导出/导入全量数据。 | 中 | ① schema.prisma 中避免使用 provider 特定的 JSON 查询，改为应用层解析 JSON；② 递归 CTE 用 Prisma `$queryRaw` 时编写兼容两库的 SQL 或准备两份；③ 迁移脚本提前编写并测试（`pg_dump` 兼容工具或自研 ETL）；④ 评估是否 MVP 直接上 PostgreSQL（Docker 部署增加一个容器，成本极低，省去迁移）。 |

### 维度三：数据库规范可行性

#### ✅ 合规项

| # | 检查点 | 评估 |
|---|---|---|
| D-OK-1 | **长表设计适配宽表** | FactRecord 长表（一行一指标一值）设计正确。将 xlsx 宽表 unpivot 为长表，消除了"新增列需改表结构"的问题，符合 1NF（每列原子值、无重复列组）。 |
| D-OK-2 | **三张事实表分离的合理性** | 经营/静态/预算来自 3 个不同 xlsx，期间维度体系不同（经营 5 个期间维度 vs 静态 4 个），强行合并会导致大量 NULL 列或 period_dim_code 语义混淆。分离是务实选择。 |
| D-OK-3 | **反范式例外有明确标注** | transaction_detail.closing_balance（冗余期末余额）、raw_json（原始行快照）均有业务理由（高频查询、追溯审计）。反范式有意识而非随意，符合"例外需有明确业务场景+严格评估"的原则。 |
| D-OK-4 | **宽表→长表行数膨胀可控** | 静态 42 列 × N 行：10 单体公司 × 34 科目 × 4 期间 = 1,360 行/批；经营 152 科目 × 12 月 × 10 公司 = 18,240 行/批。量级在万级，完全可控，无性能隐患。 |
| D-OK-5 | **period_dimension 统一表 + applicable_type** | 用 applicable_type(operating/static) 区分不同期间维度，避免建两张几乎相同的表。查询时加 WHERE applicable_type 过滤即可。设计简洁有效。 |

#### ⚠️ 风险项

| # | 检查点 | 问题描述 | 风险等级 | 改进建议 |
|---|---|---|---|---|
| D-R-1 | **唯一约束含 batch_id 导致数据膨胀** | 三张事实表的唯一约束都含 batch_id：(company_code, account_code, period, period_dim_code, **batch_id**)。这意味着每次导入都生成新行，同一逻辑数据（如"330059 公司 OP_001 科目 2024-01 月度数据"）在不同批次中重复存储。10 公司 × 152 科目 × 12 月 × 假设每月导入 1 次 × 12 个月 = ~22 万行/年，看似不大，但 3 年后 66 万行且大量是过时批次。 | 中 | ① 定义批次生命周期：批次状态 `draft → active → archived → purged`；② 看板/报表查询默认只取 `active` 批次；③ 定期归档/清理 `archived` 批次的 fact 行（保留 import_batch 元数据用于审计）；④ 新批次激活时自动将旧同类型批次降级为 `archived`。 |
| D-R-2 | **string 类型 FK（code 而非 id）的性能考量** | 全表外键使用 string code（company_code、account_code、period_dim_code）而非自增/UUID id。当前数据量（20 公司、186 科目）下性能无忧，但：(1) string 索引比 int 索引大 3-5 倍；(2) JOIN 成本更高；(3) code 变更需级联更新所有引用表。 | 低 | 数据量小，当前可接受。但需确保所有 string FK 列均有索引（Prisma 需显式 `@@index`）。若未来数据量增长到百万级 fact 行，考虑增加冗余 numeric id 作为 JOIN 键。code 变更场景应极少发生（编码是稳定标识），可接受。 |
| D-R-3 | **软删除 + 外键引用一致性** | 方案用 status 字段切换实现软删除（如 company.status = 'inactive'）。但 fact_operating 仍引用该 company_code，查询时若忘记 `WHERE company.status = 'active'`，会展示已停用公司的数据。 | 中 | ① 在 Prisma 中为所有查询默认加 status 过滤（中间件/扩展层统一注入）；② 或在 scope.ts 中将"已停用主体"排除出数据范围；③ 文档明确标注：软删除仅标记不物理删除，但所有业务查询必须过滤 status。 |
| D-R-4 | **raw_json 存储成本** | 每个 fact 行存储完整原始 xlsx 行的 JSON。粗算：18,240 行/批 × 假设每行 raw_json 平均 500 字节 = ~9MB/批。年度 12 批 = ~108MB。3 年 = ~324MB。SQLite 单文件此量级无压力，但若未来切 PostgreSQL 且数据量增长，需评估。 | 低 | 当前可接受。建议在批次归档清理时一并清理 raw_json（保留 fact 数值行，删除 raw_json 字段内容），保留可追溯性的同时控制存储。或对 raw_json 启用压缩存储。 |
| D-R-5 | **company_aggregation_map 递归嵌套的环检测** | "汇总主体可嵌套"意味着 ENZJ0001 可包含 ENZJ0002，ENZJ0002 又包含 ENZJ0001，形成环。递归 CTE 遇到环会无限递归直至栈溢出。方案未提及环检测。 | 中 | ① 写入 company_aggregation_map 时校验无环（BFS/DFS 检测）；② 递归 CTE 加 `LIMIT` 或 `depth` 计数器防止无限递归；③ PostgreSQL 可用 `WITH RECURSIVE ... AND cy.cycle = false` 环检测语法，SQLite 需应用层保障。 |

#### ❌ 问题项

| # | 检查点 | 问题描述 | 风险等级 | 改进建议 |
|---|---|---|---|---|
| D-P-1 | **双套公司编码方案是设计缺陷** | 单体公司用 6 位纯数字（330059），汇总公司用 `ENZJ` + 4 位（ENZJ0001）。同一张表、同一字段（code）混合两种编码格式，导致：(1) 排序混乱（数字 vs 字母前缀）；(2) 前端下拉选择器排序不直观；(3) 正则校验需两套规则；(4) 未来扩展新编码段（如收购新公司）时格式不统一。这不是"灵活性"，是"不一致性"。 | 中 | **统一编码方案**：全部采用 `前缀 + 数字` 格式。单体公司 `CO` + 6 位（CO330059），汇总公司 `SUM` + 4 位（SUM0001）。或全部纯数字：单体 6 位（330059），汇总 7 位（1000001，首位 1 标识汇总）。关键是统一格式规则，便于校验、排序、扩展。 |
| D-P-2 | **metric.code 与 account_subject.code 一致性约束不可实现** | 方案称"metric.code 与 account_subject.code 一致"，但 metric 表包含 `data_type: data/calc/display`。calc 类型指标（如"资产负债率 = 负债/资产"）没有对应的 account_subject 记录（它不是原始科目）。那么 calc 指标的 code 是什么？若自创编码（如 CALC_001），则与 account_subject.code 体系不一致，"一致性约束"名存实亡。 | 中 | 明确区分：① `data` 类型 metric.code = account_subject.code（一一对应）；② `calc` 类型 metric.code 使用独立命名空间（如 `CALC_资产负债率`），不强制与 account_subject 对齐；③ 在 Metric 表增加 `source_account_codes` 字段记录该 calc 指标引用了哪些科目，建立可追溯链路。 |

### 维度四：Agent/AI 约束可行性

#### ✅ 合规项

| # | 检查点 | 评估 |
|---|---|---|
| A-OK-1 | **AIProxyService 统一脱敏出口** | 前端 → AIProxyService（统一脱敏）→ LLM 的架构正确。脱敏逻辑集中在后端单一服务，前端不接触任何脱敏/还原逻辑。职责分离清晰，安全边界明确。 |
| A-OK-2 | **计算类指标 AI 辅助"仅传结构不传值"** | 指标公式 AI 辅助生成时，仅传递指标名称 + 科目结构（哪些科目、运算关系），不传实际金额值。这是正确的安全约束——LLM 只需要理解"负债总额 ÷ 资产总额"的结构，不需要知道具体数字。约束可执行且合理。 |
| A-OK-3 | **双向映射表请求级生命周期** | "每次请求生成临时映射表（公司A→330059）"，请求结束后销毁。请求级隔离避免了跨请求数据泄露，并发安全。设计正确。 |
| A-OK-4 | **ai_suggested + 人工确认闭环** | AI 生成内容标记 `ai_suggested = true`，需人工确认后才落库为正式数据。这是负责任的 AI 治理模式，防止 AI 幻觉直接进入财务口径。 |

#### ⚠️ 风险项

| # | 检查点 | 问题描述 | 风险等级 | 改进建议 |
|---|---|---|---|---|
| A-R-1 | **金额脱敏不可逆将严重削弱"AI 追加分析"价值** | 方案将金额脱敏为区间标识（"百万级"/"区间D"）。但"AI 追加分析"的核心价值在于趋势判断（环比增长/下降、同比变化、异常波动）。若 LLM 只看到"区间D → 区间D"（两期都是百万级），它无法判断趋势方向，只能输出"金额保持在百万级别，无显著变化"这类无信息量的废话。脱敏过激导致 AI 分析退化。 | **高** | **分层脱敏策略**：① 趋势方向不脱敏——传"环比 +12.3%"（百分比不泄露绝对金额）；② 变化幅度不脱敏——传"同比变化 +5%"；③ 仅绝对金额脱敏为区间。这样 LLM 能分析趋势和变化率，但不掌握具体金额。实现：AIProxyService 计算 `change_pct = (current - previous) / previous`，传百分比而非绝对值。 |

| A-R-3 | **AI 生成文字与 metric.formula 计算结果的一致性** | AI 追加分析可能写出"营收增长 15%"，但 metric.formula 实际计算结果是 12%。AI 基于脱敏数据生成，与精确计算结果产生矛盾，用户困惑。 | 中 | ① AI 生成文本时，将 AggregationService 已计算的关键指标变化率（百分比形式）注入 prompt 作为"事实约束"（"请基于以下事实撰写分析：营收环比 +12.3%"）；② AI 文本中引用数值时标注来源（"据系统计算，营收环比 +12.3%"）；③ 前端展示 AI 段落时显示 `ai_suggested` 标识 + "最终数据以指标表为准"免责声明。 |
| A-R-4 | **ai_desensitize_config 维护成本** | 配置表存储脱敏规则（config_type, pattern, replacement, enabled）。公司名脱敏需为每个公司维护正则 pattern（"浙江壹品慧贸易有限公司" → "公司A"）。公司名变更、新增公司时需同步更新配置，遗漏则脱敏失效。 | 中 | ① 公司名脱敏不依赖正则配置，改为从 company 表动态生成映射（请求时遍历所有 active 公司名替换为代号），消除配置维护负担；② 金额区间规则可配置化（区间边界可调）；③ 每次请求记录脱敏日志（哪些字段被替换），便于审计和发现遗漏。 |
| A-R-5 | **ai_suggested 确认流程的闭环细节缺失** | 方案提到 ai_suggested 标识 + 人工确认，但未描述：确认者是谁（报告作者？审批人？）、拒绝后如何处理（重新生成？手动编辑？）、确认后是否可撤销。流程不完整。 | 低 | 定义确认工作流：① AI 生成 → 标记 `ai_suggested=true, status='pending'`；② 报告作者审阅 → 接受（`status='confirmed'`）/ 拒绝（`status='rejected'`，记录原因）/ 编辑后接受（保留编辑 diff）；③ 确认后内容进入 report_section 正式版本，不可直接撤销但可通过版本回退。 |

## 五、结论与建议

### 结论

**方案不可直接进入开发，需先完成 4 项 P0 修改（预计 6 人天），完成后可进入开发。**

方案的整体架构方向是正确的：
- ✅ 技术栈选型务实（AntD 5 适配密集表格场景、Zustand+TanStack Query 状态分层、decimal.js 精度保障）
- ✅ 数据模型长表设计合理（宽表→长表 unpivot 消除 schema 脆性）
- ✅ AI 统一脱敏出口架构正确（AIProxyService 集中处理）
- ✅ 模块划分与分级策略清晰（P0/P1/P2 优先级合理）

但存在 4 个阻断级问题必须在动工前解决：
1. 前端 SheetJS 大文件解析不可行 → 改服务端解析
2. SQLite 并发写入限制 → WAL+锁 或 直接上 PostgreSQL
3. 公式引擎缺环检测 → 补 DAG 拓扑排序
4. 双套公司编码不一致 → 统一编码方案

### 建议

1. **P0 修改先行**：4 项 P0 修改预计 6 人天，建议在 T01 基础设施任务前完成方案修订，避免开发到一半返工。
2. **MVP 直接上 PostgreSQL**：鉴于 SQLite 并发限制和迁移成本，建议 MVP 阶段直接用 PostgreSQL（Docker Compose 增加 1 个容器，部署成本几乎为零），省去后续迁移的痛苦。SQLite 仅保留用于本地开发环境。
3. **AI 模块推迟到 P2 是正确的**：当前 AI 脱敏策略需重新设计（分层脱敏），不宜在 P0/P1 阶段投入。P2 阶段有充足时间完善。
4. **"预留"表述需诚实化**：i18n/多币种要么做骨架要么删掉"预留"字样，避免给团队虚假的安全感。
5. **批次治理机制必须前置**：batch_id 唯一约束会导致数据持续膨胀，批次生命周期管理（active/archived/purged）应在 T02 导入任务中一并实现，而非事后补救。
