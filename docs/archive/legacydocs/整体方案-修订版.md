### P1 建议改项（11 项）

| 决策项 | 原方案 | 修订后 | 决策依据 |
|--------|--------|--------|----------|
| **P1-1 ProTable 依赖声明** | 技术栈提及 ProTable 但未显式声明依赖 | 显式添加 `@ant-design/pro-components@^2.x`，注明 ProTable 虚拟滚动需 `scroll.y` + `pagination={false}` | 依赖未声明导致构建失败 |
| **P1-2 Tailwind preflight 冲突** | 未说明 Tailwind 与 Ant Design 样式冲突 | `tailwind.config.ts` 配置 `corePlugins: { preflight: false }`；T01 增加验证项 | preflight 重置 Ant Design 样式导致组件错位 |
| **P1-3 nginx SSE 配置** | 仅提及 SSE 流式，未说明 nginx 反代配置 | `proxy_buffering off; proxy_cache off; proxy_read_timeout 300s;` + `X-Accel-Buffering: no` 响应头 + Express 禁用 compression 对 SSE 路由 | nginx 默认缓冲导致 SSE 流式失效 |
| **P1-4 multer 安全边界** | multer 仅用于接收 Excel，无安全边界 | `fileFilter` 仅允许 .xlsx/.xls；`limits.fileSize = 50MB`；前端限制单任务上传；后端校验 MIME magic number | 无限制上传可被恶意文件攻击 |
| **P1-5 metric.code 一致性** | "metric.code 与 account_subject.code 一致"（绝对表述） | 分类型：data/display = 科目编码；calc = `CALC_` 前缀 + 业务名（如 CALC_资产负债率）；新增 `source_account_codes` 字段（JSON 数组，追溯 calc 指标引用的科目） | 计算类指标无对应科目，强制一致导致编码冲突 |
| **P1-6 批次生命周期管理** | 无生命周期管理，批次无限累积 | `import_batch` 新增 `lifecycle_status` 字段（draft/active/archived/purged）；新批次激活自动归档同 data_type 旧 active 批次；查询默认只取 active | 批次膨胀导致查询性能下降 + 历史版本混乱 |
| **P1-7 软删除查询过滤** | 软删除仅标记 status，未强制查询过滤 | Prisma 扩展层统一注入 `status = 'active'` 过滤；文档明确标注所有业务查询必须过滤 status | 软删除数据泄漏到查询结果 |
| **P1-8 汇总映射环检测** | 递归 CTE 无环检测，可能无限递归 | 写入时 BFS/DFS 环检测；递归 CTE 加 depth 计数器 + LIMIT 防止无限递归 | 汇总主体嵌套引用形成环导致查询死循环 |
| **P1-9 AI 分层脱敏** | 金额统一脱敏为区间 | **分层脱敏**：趋势方向/变化幅度（百分比）不脱敏；仅绝对金额脱敏为区间 | 百分比不泄露绝对金额，保留趋势语义提升 AI 分析质量 |
| **P1-10 AI 双管道分离** | AI 润色与追加分析共用同一脱敏管道 | **润色（polish）**：用户文本→脱敏→LLM 润色→还原；**追加分析（analyze）**：结构化指标→计算变化率→脱敏→LLM 生成→返回（无需还原） | 两者输入性质不同，脱敏策略必须分离 |
| **P1-11 双层校验收敛** | 前端 Zod + 后端 Zod 双层校验 | 校验逻辑收敛到后端单一实现（随 P0-1 一并处理） | 双层校验冗余，维护成本高 |

### P2 可选优化（8 项）

| 决策项 | 原方案 | 修订后 | 决策依据 |
|--------|--------|--------|----------|
| **P2-1 SSE+TipTap 交互** | AI 流式直接覆盖编辑器内容 | **选中→预览→确认替换**：用户选中段落 → AI 流式润色 → 侧边栏/浮层预览 → 用户确认后替换原文 | 直接覆盖破坏用户原始内容，无法对比 |

| **P2-6 公司名脱敏动态映射** | 依赖 ai_desensitize_config 正则配置 | 从 company 表动态生成映射（请求时遍历 active 公司名替换为代号）；金额区间规则可配置化 | 正则配置维护负担重，动态映射零维护 |
| **P2-7 JWT 方案** | 无状态 JWT，logout 无法真正失效 | access token 15min + refresh token 7day；logout 时 refresh token 加入内存黑名单 | 纯无状态 JWT 无法注销，存在安全隐患 |
| **P2-8 Express 版本** | Express 4/5 未锁定 | 明确锁定 Express 4.18+（LTS），package.json 锁定版本 | Express 5 破坏性变更多，4.18 LTS 稳定 |

## 一、方案概述

### 1.1 项目定位与目标

| 项 | 内容 |
|---|---|
| 项目名 | `yipinhui_finance_analytics`（浙江壹品慧财年经营数据分析 Web 平台） |
| 产品本质 | "Excel 进、看板/报表出"的内部管理口径财务数据平台 |
| 口径属性 | 内部管理口径（非审计/法定财报口径），强调灵活、可解释、可追溯 |
| 目标用户 | 财务分析师（兼it管理员）、经营层、事业部负责人、财务人员（按单体公司进行财务指标分析） |
| 核心目标 | 降低可视化门槛、统一管理口径、提升决策时效、保障可追溯、灵活可导出 |
| 单位主体 | 单主体、人民币、简体中文（MVP 不支持国际化，未来需要时另行立项） |
| 部署 | 内网私有化 Docker 单机部署（需防火墙放行 DeepSeek API 域名，见第三章部署方案） |

> [修订 P2-2] 删除原方案"i18n/多币种预留"表述。MVP 明确为单主体、人民币、简体中文，未来需要国际化时另行立项，当前不做 locale 抽象层。

**融合两份 PRD 的目标**：
- 继承 claude 版 PRD 的"4 类角色 + 13 条用户故事 + P0/P1/P2 分级"的清晰需求池与口径可追溯理念
- 继承 workbuddy 版 PRD 的"8 大模块"更完整的业务覆盖（往来分析、存货管理、AI 分析报告为差异化亮点）
- 以 system_design.md 的后端架构（Node/Express+Prisma+PostgreSQL、11 个 Service、JWT+scope 中间件、FactRecord 长表）为技术骨架
- 以 4 个 xlsx 实际业务数据结构为数据模型设计的事实依据，确保数据模型 100% 落地真实业务

> [修订 P0-2] 后端技术骨架由 SQLite 改为 PostgreSQL。

### 1.2 整合策略

两份 PRD 模块映射关系如下（claude 版 4 模块 → workbuddy 版 8 模块）：

| claude 版模块 | 整合去向（workbuddy 版） | 整合说明 |
|---|---|---|
| 导入中心 | 数据管理（Excel 导入部分） | claude 版导入校验/映射/历史版本全部并入"数据管理"模块 |
| 经营看板首页 | 首页看板 + 财务指标 | 拆分：全局 KPI 概览归"首页看板"；指标树/期间对比/趋势归"财务指标" |
| 报表中心 | 财务指标（明细表导出）+ 分析报告（模板化报告） | 交叉报表+导出归"财务指标"明细；结构化分析报告归"分析报告" |
| 管理后台 | 权限管理 + 数据管理（维度维护） | 指标/口径归"数据管理"维度维护；角色/用户/权限/日志归"权限管理" |

**整合后形成 8 大模块**（以 workbuddy 版为骨架，吸收 claude 版 P0 范围作为 MVP 必交付项）：
登录页、首页看板、财务指标、往来分析、存货管理、分析报告、数据管理、权限管理。

**分级策略融合**：采用 claude 版 P0/P1/P2 三级分级（比 workbuddy 版 3 阶段更细粒度），并映射到 workbuddy 版的 P1/P2/P3 实施阶段。

## 二、统一功能模块设计

### 2.1 模块全景图


### 3.1 技术栈冲突解决（关键决策）

**冲突点**：claude 版 PRD + system_design.md 推荐 **MUI 5 + Emotion**；workbuddy 版 PRD 推荐 **Ant Design 5**。

**统一决策：采用 Ant Design 5（+ Tailwind CSS 辅助布局）**

理由：
1. **表格/表单密集型场景**：本平台核心是财务后台，往来客商明细表、账龄矩阵表、交叉报表、存货明细等大量复杂表格，Ant Design 5 的 `Table`/`ProTable` 在分组、固定列、虚拟滚动、筛选、编辑单元格等能力远超 MUI `DataGrid`（MUI X DataGrid 高级功能需 Pro 付费版）。
2. **企业级中文本地化**：Ant Design 5 默认中文、日期选择器、金额格式化、表单校验提示更贴合国内财务场景。色标方向固定为 cn（红涨绿跌），不做 locale 抽象。
3. **表单与导入映射**：导入字段映射面板需要大量 Form 控件，Ant Design 5 的 `Form`/`ProForm` 布局与校验集成更成熟。
4. **与 ECharts 协同**：workbuddy 版已选 ECharts，Ant Design 5 与 ECharts 视觉风格更协调（同为国产体系，色板/间距风格一致）。
5. **AI 报告富文本**：TipTap 与 Ant Design 5 工具栏集成更顺畅。

**对 system_design.md 的影响**：仅前端 UI 组件层由 MUI 替换为 Ant Design 5，架构分层、后端、数据模型、API 契约完全不变。`theme.ts` 由 MUI 主题改为 Ant Design 5 的 `ConfigProvider` 主题 token。

## 四、数据模型设计（重点：深度融入 xlsx 数据）

### 4.1 设计总原则

1. **遵循三大范式**（来自 ai规范和数据库规范.md）：
   - 1NF：字段原子化（如公司主体编码与名称分离，期间维度不合并）
   - 2NF：消除部分依赖（事实表复合主键场景，非主键字段完全依赖整个键）
   - 3NF：消除传递依赖（公司名称放 company 表，科目名称放 account_subject 表，事实表只存编码外键）
   - 反范式例外：账龄区间金额等冗余字段需有明确业务场景（查询性能）+ 严格评估

2. **长表设计适配 xlsx 宽表**：xlsx 是"一行多公司多期间"的宽表，数据库采用 FactRecord 长表（一行一指标一值），**导入时在后端 ImportService 执行宽表→长表转换（unpivot/melt）**。

> [修订 P0-1] unpivot 在后端 ImportService 执行（非前端）。

3. **三张事实表分离**：经营数据、静态数据、年度预算来自 3 个不同 xlsx，期间维度体系不同（经营 5 个、静态 4 个），分表存储更清晰，符合 3NF（消除不同期间维度体系的传递依赖）。

4. **软删除查询过滤**：

> [修订 P1-7] 所有标记 `status` 字段的表（company、account_subject、counterparty、user 等），业务查询必须过滤 `status = 'active'`。通过 Prisma 扩展层（`softDelete.ts`）统一注入过滤条件，避免遗漏。

### 4.2 维度表（主数据，源自"分析主体及汇总映射.xlsx"）

#### 4.2.1 公司主体表 `company`（10 个单体 + 10 个汇总）

### 4.4 宽表→长表转换策略（FactRecord 适配 xlsx）

> [修订 P0-1] 转换流程在后端 ImportService 中执行（非前端）。

**核心问题**：xlsx 是宽表（一行多公司多期间维度），数据库 FactRecord 是长表（一行一值）。

**转换流程（在后端 ImportService 中执行 unpivot/melt）**：

1. **后端接收原始文件**：multer 接收 FormData 上传的原始 .xlsx 文件。

2. **后端流式解析**：SheetJS/ExcelJS 读取文件，识别维度列与值列（通过 MappingScheme.column_map 配置哪些列是维度，哪些是值列）。
   - 经营数据范例.xlsx：`公司名`列+`月份`列是维度，其余列是科目值列 → 每个"科目列"对应一个 account_code
   - 静态数据范例.xlsx：行是科目，列是"4 期间维度×10 公司"组合 → 拆解列头得到 company_code + period_dim_code
   - 年度预算范例.xlsx：行是科目，列是 10 家公司 → 拆解列头得到 company_code

3. **后端校验**：Zod schema 校验每行数据（校验逻辑收敛到后端单一实现，消除双层校验冗余）。

4. **行级 unpivot**：对每行数据，遍历所有值列，生成多条长表记录：
   ```
   宽表行：{公司:杭州壹品慧, 月份:2025-06, 本月收入:120000, 总成本:80000, ...}
   ↓ 后端 ImportService unpivot
   长表行：
     {company_code:CO330059, period:2025-06, account_code:OP_025, period_dim:ACTUAL_MONTH, value:120000}
     {company_code:CO330059, period:2025-06, account_code:OP_030, period_dim:ACTUAL_MONTH, value:80000}
     ...
   ```

5. **映射方案 `mapping_scheme.column_map`** 结构示例（JSON）：
   ```json
   {
     "data_type": "operating",
     "dimension_columns": {
       "company": {"source": "header", "column": "公司名"},
       "period": {"source": "header", "column": "月份", "transform": "excel_date_to_yyyy_mm"}
     },
     "value_columns": [
       {"source_column": "本月收入", "target_account_code": "OP_025", "period_dim": "ACTUAL_MONTH"},
       {"source_column": "总成本", "target_account_code": "OP_030", "period_dim": "ACTUAL_MONTH"}
     ]
   }
   ```

6. **静态数据多级列头处理**：静态数据范例.xlsx 列头为"公司+期间维度"两级，MappingScheme 需支持 `header_row_index` 配置多级表头合并。

7. **落库**：unpivot 后的长表记录批量插入（事务+批量），返回标准化结果（成功行数、错误行列表）给前端。

**PostgreSQL 递归 CTE 示例**：
```sql
WITH RECURSIVE aggregation_tree AS (
  -- 基础：直接映射
  SELECT summary_company_code, single_company_code, 1 AS depth
  FROM company_aggregation_map
  WHERE summary_company_code = 'SUM0002'
  UNION ALL
  -- 递归：汇总主体的子汇总
  SELECT m.summary_company_code, m.single_company_code, t.depth + 1
  FROM company_aggregation_map m
  JOIN aggregation_tree t ON m.summary_company_code = t.single_company_code
  WHERE t.depth < 20  -- LIMIT 防止无限递归
)
SELECT DISTINCT single_company_code FROM aggregation_tree;
```

## 八、关键设计决策与风险

### 8.1 技术栈统一决策（MUI vs Ant Design 5）

| 决策项 | 结论 | 理由 |
|---|---|---|
| UI 组件库 | **Ant Design 5** | 财务后台表格/表单密集，ProTable 分组/固定列/筛选/编辑单元格能力强；中文本地化好；与 ECharts 视觉协调；MUI X DataGrid 高级功能需付费 |
| Pro 组件 | **@ant-design/pro-components@^2.x** | ProTable 虚拟滚动需 `scroll.y` + `pagination={false}` |
| 样式 | Tailwind CSS 辅助（preflight: false） | 布局微调，不替代 Ant Design 主题；禁用 preflight 避免样式冲突 |
| 表单 | Ant Design Form（替代 react-hook-form） | 与 Ant Design 5 集成更紧 |
| 表格 | Ant Design Table/ProTable（替代 @tanstack/react-table） | 统一组件体系 |
| 后端框架 | Express 4.18+（LTS，锁定版本） | Express 5 破坏性变更多，4.18 LTS 稳定 |
| 影响 | 仅前端组件层替换 | 架构分层、后端、数据模型、API 契约不变；theme.ts 改为 ConfigProvider token |

### 8.2 数据模型与 xlsx 宽表适配策略

| 决策项 | 结论 | 理由 |
|---|---|---|
| 存储格式 | FactRecord 长表 | 聚合灵活、下钻友好、符合 3NF；沿用 system_design |
| 事实表拆分 | 三张（经营/静态/预算） | 期间维度体系不同（5 vs 4），分表消除传递依赖；查询清晰 |
| 宽表→长表 | **后端 ImportService unpivot** | 前端仅预览首100行，原始文件上传后端解析+unpivot+落库 |
| 多级表头 | mapping_scheme 支持 header_row_index | 静态数据.xlsx 列头为"公司+期间维度"两级 |
| 科目体系 | account_subject 统一表+subject_type 区分 | 经营 152 项+静态 34 项统管，3NF |
| 期间维度 | period_dimension 统一表+applicable_type 区分 | 经营 5 个+静态 4 个统管，3NF |
| 公司主体 | company 表含单体+汇总+entity_type 区分 | 汇总映射单独 company_aggregation_map 表，1NF；编码 CO/SUM 前缀区分 |
| 内部抵消 | company_aggregation_map.is_internal_elimination + counterparty.is_internal | 支持"含/剔除内部"切换 |
| 预算合并 | 独立 fact_budget 表（不并入 fact_operating） | 科目对应但期间维度体系不同，独立更清晰 |

### 8.4 风险与取舍

> [修订 P0-1] 风险项 1 更新。
>
> [修订 P0-2] 风险项 2 更新。
>
> [修订 P0-3] 风险项 3 更新。
>
> [修订 P1-6] 风险项新增批次生命周期治理。
>
> [修订 P2-4] 风险项 8 更新为外部 API 依赖。
>
> [修订 P2-7] JWT 注销限制更新。

1. **Excel 解析路径**：**服务端解析为唯一路径**。前端 SheetJS 仅预览首 100 行（`read(data, {sheetRows: 100})`），原始文件通过 FormData 上传至后端，multer 接收 + SheetJS/ExcelJS 流式解析 + 校验 + unpivot + 落库。校验逻辑收敛到后端单一实现（Zod），消除前后端双层校验冗余。multer 安全边界：fileFilter 仅允许 .xlsx/.xls，fileSize 限制 50MB，后端校验 MIME magic number，前端限制单任务上传。

2. **PostgreSQL 连接池配置**：**MVP 直接上 PostgreSQL**（生产 + Docker 部署）。Prisma provider 设为 postgresql。需注意连接池配置（`DATABASE_URL` 中 `?connection_limit=10` 或 Prisma `connection_pool_size`），避免高并发下连接耗尽。SQLite 仅保留本地开发环境可选（`provider = sqlite`，切换时注意 JSON 查询语法差异）。PostgreSQL 原生支持递归 CTE（汇总映射聚合）、JSON 查询（`->>`/`->`），是往来/存货/AI 模块的硬需求。

3. **派生指标安全（含环检测）**：禁止前端传公式字符串由后端 eval；采用白名单算子解释器（仅 `+-*/` 与指标引用）。**metric.depends_on 字段记录直接依赖的指标 code**，AggregationService 计算前构建指标依赖 DAG + 拓扑排序 + 环检测，发现环报错 `METRIC_CIRCULAR_REF`。calc 指标 code 使用 `CALC_` 前缀命名空间，避免与 data 类指标编码冲突。`source_account_codes` 字段记录 calc 指标引用的科目，建立可追溯链路。

4. **计算类指标创建流程**：计算类指标（如毛利率、周转率）由运维人员手动创建，AI可辅助生成公式建议但需人工确认后落库。AI辅助生成时仅在管理后台局部上下文中提供指标名称+科目结构，不传入实际经营数据。

5. **口径一致性**：所有派生计算唯一来源是 metric.formula + AggregationService，避免看板/报表/报告各算各的。

6. **宽表→长表转换性能**：静态数据 42 列 unpivot 后行数膨胀，需在 ImportService 批量插入优化（事务+批量）。

7. **多级表头映射复杂度**：静态数据"公司×期间维度"两级表头，mapping_scheme.column_map 需支持 header_row_index 合并；建议提供模板预校验。

8. **外部 API 依赖（DeepSeek）**：**因数据出内网，脱敏从可选变为强制**。后端 AIProxyService 直连 DeepSeek API（OpenAI 兼容接口）。风险点：(a) 网络可用性 — 内网服务器需能访问公网 `api.deepseek.com`，防火墙放行出站 HTTPS；(b) API 额度 — 需监控调用频次与 token 消耗，设置速率限制；(c) 数据脱敏强制 — 所有传入 LLM 的数据必须经分层脱敏（公司名→代号、金额→区间、变化率不脱敏）。DeepSeek API Key 存储在后端环境变量，前端不接触。SSE 流式需 nginx 反代支持（`proxy_buffering off`）。

9. **AI 模块数据脱敏（强制）**：所有接入 AI/LLM 的模块（分析报告 AI 润色、AI 追加分析、指标公式 AI 辅助生成）在调用 LLM 前**必须对公司经营数据脱敏**。**分层脱敏策略**：趋势方向/变化幅度（百分比）不脱敏；仅绝对金额脱敏为区间。**双管道分离**：润色（polish）模式输入用户文本→脱敏→LLM→还原；追加分析（analyze）模式输入结构化指标→计算变化率→脱敏→LLM→返回新文本。脱敏在服务端 AIProxyService 中统一执行。**公司名脱敏动态映射**：从 company 表动态生成映射，不依赖正则配置。

10. **批次生命周期治理**：import_batch 新增 `lifecycle_status` 字段（draft/active/archived/purged）。新批次激活时自动将同 data_type 的旧 active 批次降级为 archived。看板/报表查询默认只取 active 批次。避免批次无限累积导致查询性能下降和历史版本混乱。purged 状态仅保留元数据，事实数据可定期清理。

11. **JWT 注销限制**：采用 access token 15min + refresh token 7day 方案。logout 时将 refresh token 的 JTI 加入内存黑名单（Set/Map），阻止 refresh 续期。access token 过期后无法立即吊销（15min 自然过期），可接受。内存黑名单重启清空，若需持久化可后续升级 Redis。

12. **范围蔓延**：P1/P2 模块本期仅做接口/表预留，待客户确认后再立项排期。

13. **反范式例外记录**：transaction_detail.closing_balance、aging_record 等冗余字段需在 schema 注释中说明业务理由（查询性能）+ 一致性风险评估。

14. **xlsx 元数据变更**：若"分析主体及汇总映射.xlsx"科目体系调整，需通过 T05 维护界面更新 account_subject，影响历史数据可比性，需版本留痕。

15. **汇总映射环检测**：company.parent_code 嵌套引用可能形成环。写入时 BFS/DFS 环检测（报错 `AGGREGATION_CIRCULAR_REF`）；递归 CTE 查询加 depth 计数器 + LIMIT 20 防止无限递归。

16. **软删除查询过滤**：所有标记 status 字段的表，业务查询必须过滤 `status = 'active'`。通过 Prisma 扩展层（softDelete.ts）统一注入过滤条件。

## 九、AI 模块数据脱敏方案

> 所有接入 AI/LLM 的模块在调用大模型前，必须对公司经营数据脱敏。
>
> **[修订 P2-4]** 因改用外部公开 AI API（DeepSeek），数据出内网，**脱敏从可选变为强制**。
>
> **[修订 P1-9]** 采用分层脱敏策略：变化率（百分比）不脱敏，仅绝对金额脱敏为区间。
>
> **[修订 P1-10]** AI 润色（polish）与追加分析（analyze）双管道分离，脱敏策略不同。

### 9.1 涉及 AI 的模块清单

| 模块 | AI 用途 | 涉及数据 | 脱敏策略 | LLM 引擎 |
|------|---------|----------|----------|----------|
| 分析报告 - AI 润色（polish） | 对报告文字一键润色、风格转换 | 报告章节文本（用户自撰，可能含真实数据） | **强制脱敏**：扫描公司名→代号、金额→区间；LLM 润色后反向还原 | DeepSeek API |
| 分析报告 - AI 追加分析（analyze） | 基于数据自动生成趋势分析文字 | 本期收入/成本/利润等指标值 | **分层脱敏**：变化率（百分比）不脱敏，绝对金额→区间；无需还原（新文本） | DeepSeek API |
| 指标管理 - AI 辅助公式生成 | 辅助生成计算类指标公式建议 | 指标名称、科目结构（不含实际值） | 仅传结构不传值，无需金额脱敏 | DeepSeek API |

### 9.2 脱敏规则（分层脱敏）

> [修订 P1-9] 增加变化率数据类型，不脱敏。

| 数据类型 | 原始值示例 | 脱敏后 | 脱敏方式 | 适用管道 |
|----------|-----------|--------|----------|----------|
| **变化率（环比/同比/达成率）** | +12.3% / -5.2% | **不脱敏**（直接传"环比 +12.3%"） | 百分比不泄露绝对金额，保留趋势语义 | analyze |
| **趋势方向** | 上升/下降/持平 | **不脱敏** | 方向性描述无敏感信息 | analyze |
| 公司名称 | 浙江壹品慧科技有限公司杭州分公司 | 公司A / 主体001 | **动态映射**：从 company 表遍历 active 公司名，按出现顺序分配代号 | polish + analyze |
| 金额值（绝对值） | 1,234,567.89 | 「百万级」/「区间D」 | 按预设区间分档替换（<10万/10-100万/100-500万/500万-1亿/>1亿） | polish + analyze |
| 客商名称 | XX供应链管理有限公司 | 客商A / 客商B | 按映射表替换为顺序代号 | polish |
| 科目名称 | 燃气具-灶具收入 | 科目A / 科目B | 可选：若科目名称本身不含敏感信息可保留 | polish |

**分层脱敏设计原理**：
- **变化率不脱敏**：百分比本身不泄露绝对金额（"环比 +12.3%"无法反推原始金额），保留趋势语义可显著提升 AI 分析质量（AI 能理解"增长 12.3%"的含义，但无法理解"区间D 相比区间C 上升"）。
- **绝对金额脱敏为区间**：防止精确金额泄露到外部 LLM。
- **趋势方向不脱敏**：方向性描述（上升/下降）无敏感信息。

### 9.3 脱敏执行架构（双管道分离）

> [修订 P1-10] AIProxyService 按 `mode: 'polish' | 'analyze'` 分支处理。
>
> [修订 P2-4] AIProxyService 直连 DeepSeek API（OpenAI 兼容接口）。
>
> [修订 P2-5] analyze 模式注入事实约束。
>
> [修订 P2-6] 公司名动态映射。

```
┌──────────────────────────────────────────────────────────────────┐
│  前端（TipTap 编辑器）                                            │
│  ├─ polish: 用户选中段落文本 → POST /reports/{id}/ai/polish       │
│  │         → SSE 流式预览 → 用户确认 → POST apply-polish 替换原文  │
│  └─ analyze: 点击"AI追加分析" → POST /reports/{id}/ai/analyze     │
│            → SSE 流式生成新段落 → 展示 ai_suggested 标识           │
└──────────────────────┬───────────────────────────────────────────┘
                       │
┌──────────────────────┴───────────────────────────────────────────┐
│  后端 AIProxyService（统一脱敏入口，直连 DeepSeek API）            │
│                                                                    │
│  ┌─ mode='polish'（润色管道）─────────────────────────────────┐  │
│  │  1. 接收用户选中文本                                        │  │
│  │  2. 扫描公司名 → 动态映射（遍历 company 表 active 公司名）   │  │
│  │     → 生成临时映射表（公司A→CO330059）                      │  │
│  │  3. 扫描金额 → 分档替换为区间标识                           │  │
│  │  4. 构建脱敏 prompt → 调用 DeepSeek API（SSE 流式）         │  │
│  │  5. 接收 LLM 返回 → 反向还原（代号→原始公司名）             │  │
│  │     （金额区间不还原，LLM 返回文字不会含精确金额）           │  │
│  │  6. 返回还原后的润色文本给前端预览                          │  │
│  └────────────────────────────────────────────────────────────┘  │
│                                                                    │
│  ┌─ mode='analyze'（追加分析管道）────────────────────────────┐  │
│  │  1. 接收 section 上下文 + 请求的指标范围                    │  │
│  │  2. 从 AggregationService 获取结构化指标数据                │  │
│  │  3. 计算变化率（环比/同比百分比）                           │  │
│  │  4. 分层脱敏：                                              │  │
│  │     - 变化率 → 不脱敏（直接传"环比 +12.3%"）               │  │
│  │     - 绝对金额 → 分档替换为区间                            │  │
│  │     - 公司名 → 动态映射为代号                              │  │
│  │  5. 注入事实约束（关键指标变化率作为 prompt 约束）：         │  │
│  │     "以下为已确认的数据变化率，你的分析必须与此一致：       │  │
│  │      收入环比 +12.3%，成本环比 +8.1%，毛利率提升 2.3pct"    │  │
│  │  6. 构建脱敏 prompt → 调用 DeepSeek API（SSE 流式）         │  │
│  │  7. 返回新文本（无需还原，纯新文本）                        │  │
│  │  8. 标注 ai_suggested=true                                  │  │
│  └────────────────────────────────────────────────────────────┘  │
│                                                                    │
│  DeepSeek API Client（OpenAI 兼容接口）                            │
│  ├─ baseURL: https://api.deepseek.com/v1                          │
│  ├─ model: deepseek-chat (flash)                                  │
│  ├─ apiKey: process.env.DEEPSEEK_API_KEY                          │
│  └─ stream: true（SSE 流式）                                      │
└──────────────────────────────────────────────────────────────────┘
```

**关键设计**：
- **脱敏在服务端统一执行**：AIProxyService 是唯一出口，前端不接触脱敏/还原逻辑
- **公司名动态映射**：每次请求时从 company 表遍历所有 active 公司名，按出现顺序生成临时映射表（公司A→CO330059），LLM 返回后按映射表还原（polish 模式）。消除 ai_desensitize_config 正则配置维护负担。
- **金额脱敏不可逆**：金额分档后 LLM 只知道"百万级"，返回的文字不会包含精确金额，无需还原
- **变化率不脱敏**：百分比不泄露绝对金额，保留趋势语义提升 AI 分析质量
- **事实约束注入**：analyze 模式将 AggregationService 已计算的关键指标变化率注入 prompt，约束 AI 文本与真实数据一致
- **DeepSeek API 直连**：后端 AIProxyService 直连 DeepSeek API（OpenAI 兼容接口），API Key 存环境变量，前端不接触

### 9.5 计算类指标 AI 辅助创建流程

```
运维人员在管理后台新建计算类指标
  ├─ 1. 输入指标名称（如"增值业务毛利率"）
  ├─ 2. 选择关联科目层级（增值业务收入、增值业务成本）
  ├─ 3. 点击"AI辅助生成公式" → AIProxyService
  │     ├─ 仅传入：指标名称 + 科目名称 + 科目层级结构（不传实际数值）
  │     ├─ 调用 DeepSeek API → 返回公式建议
  │     └─ 如 "增值业务毛利率 = (增值业务收入 - 增值业务成本) / 增值业务收入 * 100%"
  ├─ 4. 运维人员审核/修改公式
  ├─ 5. 系统解析公式 → 自动填充 metric.depends_on + source_account_codes
  ├─ 6. 环检测（DAG 拓扑排序，发现环拒绝保存）
  ├─ 7. 确认落库 → metric 表 (code=CALC_增值业务毛利率, created_by=运维人员, ai_suggested=true)
  └─ 8. 记录口径历史 → metric_definition_history
```
