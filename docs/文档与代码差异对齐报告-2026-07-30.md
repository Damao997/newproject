## 一、优秀改进（应保留，需补文档）

### A1. 中间件链下沉到路由级
- **规范**：`CLAUDE.md`「中间件执行链」/`整体方案v3.md` §3.4 描述为单一 8 步全局链（helmet→cors→json→限流→auth→permission→scope→softDelete→audit）。
- **代码**：`app.ts` 全局仅装配 `traceId → 访问日志 → helmet → cors → express.json(1mb) → /api/v1 通用限流 → 路由 → 404 → errorHandler`；`auth/permission/scope/softDelete/audit` 在各路由内叠加。
- **价值**：公开端点（`/auth/login`、`/auth/refresh`、`/health`）不被鉴权误拦；权限声明与端点同处一行，可读性与审计性更好。
- **额外增强**：`traceId` 最先执行（贯穿日志与错误响应）、结构化访问日志（user/ip/耗时）、`trust proxy 1`。
- **一致性**：与 `lib/response.ts` 的 `traceId` 注入、`docs/references/observability.md` 一致。

### A2. 统一响应体附加 `traceId`
- `lib/response.ts` 的 `sendOk`/`sendFail` 在 `{code,data,message}` 之外注入 `traceId`，前后端与日志可串联排障。规范未要求，属正向增强，已被 `app.test.ts` 断言覆盖。

### A3. 左侧侧边栏布局替代顶部导航
- **规范**：`frontend-design-proposal.md` §5.1 顶部 Header(56px) 承载导航。
- **代码**：`components/layout/main-layout.tsx` + `sidebar.tsx`：桌面端 `w-60`/收起 `w-16`（localStorage 持久化）、移动端抽屉、顶栏 `h-14` 仅放财年选择与用户菜单，内容区 `max-w-7xl`。
- **价值**：8 个一级模块用顶部导航会拥挤；侧边栏 + 收起态更适合后台密集数据场景；侧边栏项按 `usePermission` 过滤（对齐安全规范 §2.2）。

### A4. 嵌入式 PostgreSQL 本地开发链路
- `scripts/local-db.ts`（`embedded-postgres`，PG17，数据落 `server/.pgdata`）+ `npm run setup` 一键初始化，实现"零 Docker、零管理员权限"上手。规范 §1 只描述 Docker 化 PG15，未区分本地/生产。

### A5. 环境变量可运维化扩展
- `.env.example` 新增 `ACCESS_TOKEN_TTL`/`REFRESH_TOKEN_TTL`/`LOG_LEVEL`/`FISCAL_START_MONTH`/`SEED_DEFAULT_PASSWORD`/`ENTERPRISE_INFO_PROVIDER`；`FRONTEND_ORIGIN` 支持逗号分隔多值白名单（仍禁通配符）。

### A6. AI 能力超出规范范围且守住安全约束
- 规范外新增但实现完整：`report-summary`（章节摘录→总体概述初稿）、公式批量检测（≤30 条，规则校验＋LLM 语义审查）、公式规则 CRUD、`batch-preview`/`batch-apply`、公司名映射 60s 缓存、单趟 alternation 正则替换（防子串污染）。
- 安全约束未被牺牲：四层 Prompt 防护、脱敏→还原闭环、公式管道仅传科目结构不传数值、AI 输出全部经 `filterOutput` 检测编码泄露。

### A7. 数据模型对业务的必要扩展（已进规范 v1.1）
- `account_subject.value_type`（amount/quantity/ratio 分型渲染）、`subject_type` 增 `transaction`、`counterparty.party_type`、`user.data_scope_codes`（多选数据范围）、`import_batch.detail_count`/`coverage_json`、`transaction_detail` 11 列账龄（已在规范 1.5 节登记反范式例外）。

### A8. Schema 命名合规的机械化守护
- `server/scripts/check-schema-naming.mjs` + `lint-staged.config.mjs` 在 pre-commit 校验 `schema.prisma` 命名，防止文档-代码再次漂移。规范 v1.1 已成文。

## 二、问题变更（需修正）

> 按修复优先级排序。P0=阻断交付/安全基线，P1=本周，P2=下迭代。

### B1【P0】部署物料全部缺失
- **规范**：`部署运维规范.md` §1（compose 四服务 postgres/backend/frontend/db-backup）、附录 B/C（Dockerfile×2）、§2（nginx.conf）、§3（`init-roles.sql`：`yipinhui_app` 仅 DML + 审计表防篡改）、§5（`backup.sh`：日全量＋小时 WAL＋AES 加密）。
- **实测**：`docker-compose.yml`/`server/Dockerfile`/`web/Dockerfile`/`nginx.conf`/`backup.sh`/`server/prisma/init-roles.sql` **均不存在**（`server/prisma/init-audit.sql` 存在，仅覆盖审计表分区/最小权限的一部分）。
- **影响**：违反 `整体方案v3.md` §2.7 P0 安全基线中的"DB 最小权限"与"每日全量备份"两项；内网交付链路为零。技术债最高的一项。
- **建议**：按规范原文创建 6 个文件（规范已含可直接落地的完整内容），并把 `init-audit.sql` 的执行纳入 compose 初始化目录；`server` 增 `migrate:deploy` script。工作量 1-2 人日。

### B2【P1】`GET /indicators/periods` 缺少 `requirePermission`
- **规范**：`安全与权限规范.md` §3.2「所有受保护路由必须声明资源编码」＋默认拒绝原则。
- **代码**：`server/src/routes/indicators.ts` L63 仅经 `router.use(authenticate)`，无 `requirePermission`；同文件其余 6 个端点均已声明。
- **影响**：任意已登录用户可读期间列表（数据敏感度低），但破坏"权限声明全覆盖"这一可审计性前提。
- **建议**：改为 `router.get('/periods', requirePermission('indicators:view', 'view'), ...)`。1 行修改，无兼容风险（`indicators:view` 已在全部相关角色的 seed 权限内）。

### B3【P1】审计日志缺 `user_agent`（schema + 代码双缺）
- **规范**：`安全与权限规范.md` §12.1 审计字段含 `user_agent`。
- **代码**：`schema.prisma` `model AuditLog` 无该列（L755-L770）；`middleware/audit.ts` `recordAudit` 也未采集。
- **影响**：安全事件取证能力受限（无法区分同 IP 不同客户端）。
- **建议**：二选一并落文档 —— (a) 加 migration 补 `user_agent VARCHAR NULL` 并在 `recordAudit` 从 `req.headers['user-agent']` 截断（≤512 字符）写入；(b) 若判定 IP+traceId 已够，则从规范 §12.1 删除该字段。**推荐 (a)**，成本约 0.2 人日。

### B4【P1】健康检查路径与部署规范不一致
- **规范**：`部署运维规范.md` §1 compose healthcheck、§2 nginx `/api/v1/health` 反代、§6 `routes/health.ts` 均使用 `/api/v1/health`。
- **代码**：`app.ts` L51 定义顶层 `GET /health`（刻意置于限流/鉴权之前），`app.test.ts` L64-L73 断言该路径；不存在 `/api/v1/health`。
- **影响**：若按现有规范文本编写 compose/nginx，容器健康检查将 100% 失败 → 部署期故障。
- **建议**：保留代码 `/health`（探针不应走 `/api/v1` 限流），**改规范**：compose healthcheck 指向 `http://localhost:3001/health`，nginx 增 `location = /api/v1/health { proxy_pass http://backend/health; }` 兼容外部探针。

### B5【P2】`permission.action` 为 String 而非 ENUM
- **规范**：`数据模型规范.md` §7.3 `action` 为 ENUM(view/create/update/delete/export/import)；`CLAUDE.md` 同。
- **代码**：`schema.prisma` L651 `action String`。
- **影响**：值域无库级约束，拼写错误的权限记录会静默变成"永不命中"的死权限（`requirePermission` 精确匹配 `resource+action`）。
- **建议**：新增 Prisma enum `PermissionAction` + migration（`permission` 表数据全部由 seed 生成，迁移风险低）；同时在 `AdminService` 的角色权限编辑入口加 zod 枚举校验。若不改库，则必须在规范中把该字段降级为「String + 应用层枚举校验」并说明理由 —— 不允许继续维持文档与库不一致。

### B6【P2】前端 2 处硬编码金额格式
- **规范**：`CLAUDE.md`「金额展示」要求统一走 `formatMoney`/`formatMoneyWan`。
- **代码**：`web/src/pages/transactions/import-dialog.tsx` L17-L18（`(v/10000).toFixed(2)万`）、`trend-card.tsx` L145（`v.toFixed(2)`）。
- **影响**：与"首页/指标页去'万'字"「百分比 1 位小数」等既定规范产生视觉不一致；后续调整精度需多点同步。
- **建议**：改用 `lib/utils.ts` 的 `formatMoneyWan`/`formatMetricValue`。

### B7【P2】Chunk 体积超阈值
- `vite.config.ts` `manualChunks` 中 `vendor-charts`(echarts，约 1.1MB) 与 `vendor-excel`(exceljs+xlsx，约 938KB) 远超规范 §7.3「首屏 gzip < 150KB」的意图。
- **建议**：ECharts 改按需注册（`echarts/core` + 所需 chart/component），导出库（exceljs/xlsx/jspdf/docx）改为触发导出时动态 `import()`。ProTable 已是懒加载的正确范例，可复用其模式。

### B8【P2】残留文件与 mock 数据
- `web/logo.png`（65KB，代码引用的是 `public/logo.png`）、`web/demo.html`（23KB）、`web/src/assets/{react.svg,vite.svg,hero.png}`、`web/src/mock/{data,operating-analysis,static-analysis}.ts` 均零引用。
- **建议**：删除模板残留；mock 数据若仍有参考价值移至 `docs/data-templates/samples/`。

### B9【P2】`metric-values.ts` 无测试；KPI `unit === '%'` 隐式约定
- `calcYoy`/`calcAchievement`/`calcYtdYoy` 缺分母为 0、负值、null 的边界测试（`web/src/lib/` 下无对应 `.test.ts`）；KPI 卡片依赖 `data.unit === '%'` 字符串判定值型，而后端已有 `valueType` 分型能力。
- **建议**：补边界用例；KPI 改用 `valueType` 判定，或在 `KpiData` 类型注释中固化约定。

**关键决策**：**不使用 Prisma 自动生成的迁移** —— 其对枚举转换采用 drop+add，会**清空 permission 表**。手写 `USING` 转换保住了存量数据。

**迁移后实测**（`scripts/verify-audit-permission-migration.ts`）：178 条权限行完整保留、6 角色不变、7 枚举值就位、非法 action 被库级拒绝、`user_agent` 为 `varchar(512) NULL`。

**顺带发现并修补的真实漏洞**：`PUT /admin/roles/:id/permissions` 此前把 `req.body.permissions` **无任何校验**直送 `prisma.createMany` —— 任意 `resource`/`action` 字符串均可落库，非法 action 还会让 PG 抛 22P02 变成 500。现校验 action 枚举 + resource 二/三段式格式（`^[a-z0-9-]+(:[a-z0-9-]+){1,2}$`）+ 条目上限 500。
