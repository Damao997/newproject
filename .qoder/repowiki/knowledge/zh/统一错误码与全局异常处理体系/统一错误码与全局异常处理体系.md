该后端服务采用「自定义异常类 + 全局中间件 + 统一响应结构」的三层错误处理架构，所有错误均通过 `AppError` 向上抛出，由 Express 全局错误中间件统一分类、记录并转换为标准 JSON 响应。

### 1. 系统/框架
- **Express** 作为 Web 框架，通过挂载在路由末尾的错误处理中间件捕获所有未处理异常。
- **Prisma** 客户端异常（如唯一约束冲突 P2002、记录不存在 P2025）被中间件显式映射为业务错误码。
- **Zod** 参数校验失败以 `ZodError` 形式抛出，中间件将其转为 400 错误。
- **multer** 文件上传异常（如 `LIMIT_FILE_SIZE`）也被单独识别并返回 400。

### 2. 核心文件与职责
- `server/src/lib/errors.ts`：定义 `AppError` 类及 `errors.*` 工厂函数（badRequest/unauthorized/forbidden/notFound/conflict/tooManyRequests/internal），封装 code 与 httpStatus 双字段。
- `server/src/middleware/error-handler.ts`：全局错误处理中间件，按类型分流 AppError → 自身 code/http；ZodError → 400；Prisma 已知错误 → 409/404；未知异常 → 500。同时提供 `notFoundHandler` 处理未匹配路由。
- `server/src/lib/response.ts`：统一响应结构 `ApiResponse<T>` 与 `sendOk`/`sendFail` 两个构造器，确保所有接口返回 `{ code, data, message, traceId }`。
- `server/src/lib/async-handler.ts`：异步路由包装器，将 Promise reject 转发给 Express 错误中间件，避免未捕获拒绝。
- `docs/references/errorcode.md`：规范文档，定义 HTTP 状态码映射、错误码分段（10000–19999 参数、20000–29999 业务、30000–39999 认证授权、40000–49999 第三方、50000–59999 系统）及异常处理策略。

### 3. 架构与约定
- **异常上抛**：业务层不直接调用 `res.status().json()`，而是通过 `throw new AppError(code, httpStatus, message)` 或 `errors.xxx(...)` 抛出，由中间件统一处理。
- **HTTP 状态码与业务码分离**：`sendFail(res, code, message, httpStatus)` 允许业务错误码（如 40000 AI 错误）与 HTTP 状态码（如 502）独立设置。
- **traceId 贯穿**：每个请求生成唯一 traceId，错误日志与响应体中均携带，便于链路追踪。
- **外部依赖错误**：DeepSeek 调用失败抛出 40000/502 或 40001/503，由中间件记录后返回通用消息，不泄露堆栈。
- **404 兜底**：未匹配路由由 `notFoundHandler` 返回 404，位于 `errorHandler` 之前。

### 4. 约定与约束
- **禁止吞异常**：中间件注释明确「禁止吞异常」，所有未捕获异常必须记录日志并返回 500。
- **500 不暴露细节**：未知异常仅记录完整堆栈到日志，向客户端返回通用「服务器内部错误」。
- **参数校验失败一律 400**：Zod 校验失败取第一条错误信息拼接路径作为 message。
- **第三方错误重试策略**：规范文档规定第三方错误需记录日志 + 指数退避重试（≤3 次），当前 DeepSeek 客户端已实现超时中断与错误转换。
- **成功响应 code=0**：`sendOk` 固定返回 code=0，非 0 表示错误，前端据此判断成功/失败。
